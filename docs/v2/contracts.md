# Atlas v2: build contracts

> The shapes every lane builds against. Written in Wave 0 (2026-10-09) from the approved scope
> and the research notes.
> A lane that needs a shape not written here stops and asks the orchestrator; it does not invent one.
> Changing a contract after Wave 1 starts = an orchestrator decision recorded in the build log.

Conventions: Python 3.12 (`py -3.12`), stdlib + `pyyaml` only (no new dependency without the orchestrator).
Paths below are relative to the repo root unless absolute. Python module names are as imported by
the server, which puts `cockpit/` and `dashboard/` on `sys.path` (so `import ledger2.query`,
`import plan.api`, `import teamlive`, `import usage`). Times are local ISO-8601 with seconds and
offset (`2026-10-09T14:20:05+02:00`). Every JSON API answers `{"ok": true, ...}` or
`{"ok": false, "error": "<one line>"}` with the HTTP code given per endpoint.

## 1. The ledger: events

**Where:** `<data>\ledger\` (outside the repo; override `ATLAS_LEDGER2_DIR` for tests, which
MUST use a temp dir). Layout:

```
ledger/
  events-YYYY-MM-DD.jsonl   append-only, one JSON object per line, never rewritten, never pruned
  v1/events.jsonl           the imported v1 dispatch history (§1.6), regenerated by the importer only
  state/<session_id>.json   the hooks' per-session cache (§1.4), rebuildable from events, may be deleted
  state/offsets-<sid>.json  per-session transcript offsets + recent message ids for cost capture (§1.5)
  auto/<marker>.json        automatic-session markers written by the launcher (§7)
  .lock                     the append lock file
```

**Writing:** one line per event, UTF-8, `ensure_ascii=False`, < 4 KB (truncate any string field to
200 chars before writing). Lock = open `.lock`, `seek(0)`, `msvcrt.locking(fd, LK_NBLCK, 1)` in our own
loop, 20 tries × 50 ms; if not obtained, proceed without it: never lose an event, never block a
session. The cost pass (§1.5) reads transcripts OUTSIDE the lock; only its appends and its
offsets/state write take it. The hook holds that lock across **read state → append event(s) → write state**
(`state/<sid>.json.tmp` then `os.replace`), so concurrent hook processes (parallel tool calls) never
lose a version bump or a pending entry. Each append = the file opened in append mode and ONE
`write()` of the whole line.
**Hash chain (amendment, screen review 2026-10-09; see §6.4 rule A):** every line carries `prev` =
the sha256 (hex) of the PREVIOUS line's bytes in the same day file, without its line ending; the first
line of a day carries the sha256 of the last line of the nearest earlier day file, or `"genesis"` when
none exists. The append computes it under the lock (`store.append_events`, and the hook's own
`append_lines`). `store.verify_chain()` walks the day files in order and returns `{intact, breaks:
[{file, line}], files, lines}`; lines written before the chain existed (no `prev`) are accepted until
the first chained line. A deleted or edited line shows as a break at the line AFTER it; `verify_chain` accepts a `prev` equal to the hash of
any of the previous 8 lines ONLY for a line flagged `nolock` (appends that raced without the lock chained to a slightly
stale tail), for the first line of a day file (backfill shape) and for the first chained line after legacy lines; every
other line must link to the line right before it, so lines inserted without `nolock` produce a break. The lock is retried for
~3 s before an append proceeds without it, and such lines carry `"nolock": true`; every append is one `write()` on an
O_APPEND handle, and a line still being written by another process is not used as the tail. Limits: the
last line of the newest file can be cut or edited without a trace, and an event appended to a day file
that already has a later neighbour (backfill) reports a break; the chain makes tampering visible, it
does not prevent it.
**Break triage and acknowledgement (decision 2026-10-10).** The walk lives in the stdlib-only
`cockpit/ledger2/ledger_chain.py` (the installer copies it next to the hook, like `areas.py`). A break has a stable id
`<day>:<line>:<hash8 of the broken line>:<hash8 of the previous non-blank line in scan order>` (for example
`2026-10-09:120:ab12cd34:9f00e1a2`); binding the predecessor means that editing the line before an acknowledged break
makes it a new, unacknowledged one. For every break the code computes, deterministically and without a model, signs of
an accident (6 shown: within the last 8 lines of the day file; flagged `nolock`; cut off or unreadable; time within 1 s
of a neighbour; `prev` points to another existing line; the previous day file ends earlier than this line expects) and
signs of tampering (in the middle of the history and not flagged; `prev` matches no line; a `refusal`, a NEEDS CHANGES
`verdict` or a `bypass_attempt` right next to the break), then a verdict "Looks accidental: N of 6 signs: ..." /
"Looks like tampering: ..." / "Unclear: ...". `nolock`, end-of-file position and same-second time are signs only, never
sufficient. Rules: (i) `prev` matching NO line is never accidental: tampering, or unclear when the line is flagged
`nolock` or the previous day file ends earlier than expected; (ii) a cut-off line is accidental only if the next
non-blank line (same or next file) has `prev` equal to the hash of the cut-off line or of the line before it, or the
cut-off line is the last line of the ledger, else unclear; (iii) a `prev` pointing to another existing line is
accidental only if that line or one of the 8 before it carries `nolock`, or it is the backfill shape (first line of a
day file pointing into the previous day file), else unclear. An acknowledgement (`integrity_ack`) counts only if its own
line is not a break, it has no `agent_id`, `by` is `operator`, and the latest prompt event of the same `sid` has
`cmd` = `ack-break`. Status: "intact" (no break), "intact, N acknowledged" (every break acknowledged) or "broken"
(any unacknowledged break); a NEW break is unacknowledged, so it turns the status red again.
**Plain limits of the chain.** There is no secret key: whoever can write the files can re-chain every line from an edit
point to the end, and that leaves NO break. The chain finds crude edits, insertions, deletions and reorderings, nothing
more; the window tolerance exists only for `nolock` lines. An edit to the newest lines of the newest file cannot be
detected until the next write chains onto it.
**Outside anchor.** Detects edits to closed days of the ledger, including a full re-chain, as long as the GitHub ruleset
stays in place. Pushes use the operator's existing account SSH key (no passphrase prompt); removing the ruleset needs a browser
session logged in to GitHub, which is the one thing to keep away from agents. The ruleset also requires linear history. How it works: `tools/anchor_ledger.py` runs daily (Windows task `AtlasLedgerAnchor`, 21:00) and
appends `{day, lines, last_hash, anchored_at}` (plus `head: true` while the day is still open) for the last
newline-terminated, non-blank line of each day file to `anchors.jsonl` in a separate public git repo (hashes only), commits, and runs
`git push <pinned url> HEAD:main`. The pinned remote lives in the versioned file `anchor.json` at the Atlas root
(`url` = `git@github.com:example/atlas-anchor.git`, `branch`, `clone` = `D:\AI\atlas-anchor`; the clone path can be
overridden with `ATLAS_ANCHOR_REPO`; the file named by `ATLAS_ANCHOR_CONFIG` replaces it, for tests). The GitHub branch
ruleset blocks force pushes and deletions. The tool never prompts (`GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, SSH
`BatchMode=yes`), never rewrites or "corrects" an entry, and exits non-zero on a mismatch (2), a commit or push failure
(3) or a setup error (1: no git, no clone, no config).
**The local file is not trusted.** The integrity check runs `git fetch <pinned url> main` in the clone from a background
thread (cached, TTL 10 minutes, never inside a request) and builds the anchor set from the whole remote history of
`anchors.jsonl`: every version must be a byte-prefix of the next one, any other change is broken, "Looks like tampering:
the outside anchor file was rewritten." The local file must equal the remote file plus not-yet-pushed appends, else
broken, "the local anchor file differs from the outside copy". Each entry says "the Nth non-blank line of that day file has
this hash"; a changed or missing line is broken, never acknowledgeable, never "accidental": "Looks like tampering: the
record of <day> no longer matches its outside anchor of <date>". An entry that is not a valid object (day `YYYY-MM-DD`,
`lines` a positive integer, `last_hash` 64 hex, `anchored_at` ISO) or a final line without its newline is reported as
"an anchor entry is unreadable", never dropped. Remote unreachable is amber (`remote: "unreachable"`, `unreachable_since`),
never a silent fallback to the local file. The payload `anchor` holds `{configured, expected, missing, last_anchored_day,
last_remote_commit_at, last_push_ok_at, remote, unreachable_since, mismatches[]}`; the panel shows amber when the newest
remote commit is older than 2 days and red when older than 7 days.
**Hardening of the check.** The fetch goes into a fresh temporary bare repo (never the clone), with no system or global git
config, `protocol.allow=never` except ssh, `core.autocrlf=false` and a forced `GIT_SSH_COMMAND=ssh -o BatchMode=yes`; the
push uses the same environment plus `remote.pushDefault=`. A `url.*` key in the clone's own config is tampering. Any
merge commit in the fetched history is tampering (history is read with `--full-history`, all versions in one
`git cat-file --batch`). The tool commits `.gitattributes` with `anchors.jsonl -text` and compares the local file with
`git show HEAD:anchors.jsonl`, so a CRLF checkout is not an edit. Unreachable remote: amber, red after more than 2 days once
`anchor_configured` exists, and never rendered as "all match". With `anchor_configured` present, `ATLAS_ANCHOR_DISABLE` or
`ATLAS_ANCHOR_CONFIG` in the cockpit environment shows amber "check disabled". The Edit and Write tools are denied on the
clone path, and the Bash guard lets only `tools/anchor_ledger.py` name it.
**Limits.** This raises the bar against accidental or clumsy tampering; it is not proof against an agent that can edit
Atlas's code, `~/.ssh/config` or `known_hosts`, or drive a browser logged in to GitHub.
**"Configured" only grows.** On the tool's first successful push it appends one `anchor_configured` event to the ledger
(`url`). Once that event exists, a missing config, clone or `anchors.jsonl`, or an empty anchor set, is broken: "Outside
anchor missing". With no event and no anchor file the panel says "Outside anchor: not set up" and the status is unaffected.
**Still open:** lines written after the last anchor run (today's open day) are covered only from the next run; whoever
holds the operator's GitHub login can remove the ruleset and then rewrite the remote; and anyone who can write the PC can stop the
daily task (the staleness warning is the only signal).
**Metadata only: never prompt text, never tool input text, never tool output text**, except the fields
explicitly listed below (task labels ≤ 60 chars, the orchestrator's summary, paths of edited files).
The denied command itself is NEVER stored, not even for `bypass_attempt` (decision 2026-10-10): the hook
classifies it in memory and keeps only derived labels (`effect`, `target`). The one free-text field a
`bypass_attempt` carries is `desc`, the agent's own stated intent (the Bash `description`), clipped to 160 chars
and masked BEFORE the clip, because an agent's words can hold secrets too: any `NAME=value`, `NAME: value` or
`set|export|-e NAME value` whose name contains `password`, `passwd`, `pwd`, `token`, `secret`, `api_key`,
`access_key` or ends in `_key`; `--password`/`--token` style flags; `-u user:pass`; URL credentials
(`scheme://user:pass@`); `Authorization:`/`Authorization=` and `Bearer` values; `mysql -pSECRET`;
`sshpass -p SECRET`; `sk-`/`pk-`/`glpat-`/`xox?-`/`ghp_`/`gho_`/`ghs_`/`ghu_`/`github_pat_`/`npm_`/`hf_`/`AKIA`/
`AIza` tokens; and hex or base64-like runs of 24+ characters (a run with `/` is kept only when every `/`-piece
looks like a path name). Only the first 4096 characters are processed.
**Trust rule for reports:** facts in a bypass report are computed by code from the ledger and can be trusted; a
note (`bypass_note`) is the main session's account of the events, to be read with care, and never overrides the
facts.

**Helper type `advisor`** (since go-live, see the build log). Not an event kind: `advisor` is a helper type that is neither a builder nor a reviewer (in no `builders` or `reviewers` list and in no crew). Its `helper_start`, `helper_end` and `cost` events are recorded like any helper's (`helper: "advisor"`, `model` a Fable model id); it never produces a `verdict`, never a rework round, and never marks changes as checked. The spawn description (the `helper_start` label) starts with `scope:`, `unstick:` or `design:` by convention, which the weekly report reads. The weekly report's Advisor section compares consult tasks with no-consult tasks matched on k, the rounds before the first consult: per k, consult tasks' rounds after the consult against no-consult tasks' rounds after their k-th round; legacy verdicts without `round` count per distinct failing version.

The `task` field is the **current task id** of the session at the time of the event (or `null` if no
task is open). A task id is `<first 8 chars of sid>-<n>`, `n` = 1, 2, ... in order of the task-opening
events (`work_type`, `playbook`, implicit `undeclared`) in that session. `derive` takes the id from
the opening event's `task` field and never recounts.

Task-opening rules:
* `: team-type <type>` with an optional second word = area id (`: team-type coding atlas`). The area
  word is optional; `team_events.py`'s regex is widened (one-line change, Lane 1) so the Team panel
  keeps its type label.
* `: team-type <type> [area] [task:<id>]` (since 2026-10-10): an optional LAST token `task:<id>` links the task to a
  Plan item. `<id>` is a calendar event id (`evt_` + 8 hex), a series occurrence (`evt_xxxxxxxx@YYYY-MM-DD`), a
  `tasks.yaml` id (`t_` + 8 hex) or a project plan.yaml id (`<project>/<task id>`). Order is area then task; the task
  token may be given without an area. The id is stored on the `work_type` event as `plan_ref` and in the hook state
  (`plan_ref`); the format is validated (the value is stored exactly as validated, case-sensitive in both hooks), the arguments are capped at 120 characters (longer = `ignored` bad arguments) and parsed by splitting words, never by a backtracking regex, and free text is never stored: a malformed id is logged as
  `ignored {what: "team-type: bad plan ref"}` and the type is still declared (no `plan_ref`). `team_events.py`
  (the Team panel's log) records the same validated `plan_ref` on its `WorkType` record, and logs no `WorkType` at all when the declaration fired inside a helper (the Team panel also drops any such record on read). The id is NOT checked
  against the Plan at declaration time (the hook never reads the Plan); it is resolved on read (§1.7, §5.1).
  `tools/find_plan_item.py "<name words>" [--day YYYY-MM-DD]` finds the id (§5.3).
* **Automatic Plan link** (since 2026-10-12): when the hook opens a `playbook` or `work_type` task WITHOUT an explicit `task:<id>`, it looks for the Plan item the session was run for. Never for the implicit `undeclared` task; an explicit `task:<id>` always wins and is unchanged. Candidates are today's calendar events (`GET <plan_url>/api/v2/plan?from=<today>&to=<today>`, section 5.3) with the SAME area as the task being opened, with a start and end time (all-day skipped), not `done`, and running now or starting within 15 minutes (`start - 15 min <= now < end`, local time). Exactly one candidate links; zero or several = no link (never a guess). The ref is the row's id: `evt_xxxxxxxx` for a single event, `evt_xxxxxxxx@YYYY-MM-DD` (the row's `occurrence`) when the row has `recur`; it is validated with the same pattern as an explicit ref. It is stored as `plan_ref` plus `plan_auto: true` on the opening event, at task open only (never revised later); `derive` copies both into the TaskRecord (`plan_auto`, false when absent). `plan_url` comes from `hooks/atlas_config.json` (key `plan_url`, default `http://127.0.0.1:8765`), overridden by the env var `ATLAS_PLAN_URL`; a present-but-empty, null or `off` value (either place) switches the feature off, the default URL applies only when the key is absent; only a loopback host (127.0.0.1, ::1, localhost) is used, with no proxy; a malformed `task:` token counts as explicit (no automatic link); helpers never trigger the read; an automatic ref is not an explicit one for the 60 s duplicate rule (an explicit `task:` after it re-opens the task); `install_hooks.py` keeps an installed `plan_url`. The read is stdlib `urllib` with a 0.5 s timeout per socket operation (redirects are not followed: a 30x means no link), done BEFORE the ledger transaction (never under the lock), only when a bare declaration or playbook is about to open; any failure (server down, bad JSON, timeout) = no link, silently, and the hook never reads `schedule.yaml`.
* An explicit declaration always opens a **new** task, even with the same type as the open one (the old
  task is closed as `switched`, or `abandoned`, see "Declaring over an open failing review"). Under the rules there, a
  declaration over a task with an open failing review abandons it or carries its count; otherwise it starts fresh. **Resolved**
  (2026-10-10) = the task's most recent reviewer verdict is READY and that READY covers the latest main-session version
  (`last_verified >= version`) AND whose reviewer was LAUNCHED after the latest NEEDS CHANGES arrived (a reviewer started
  in parallel with the failing one cannot clear it: A and B launched together, A answers NEEDS CHANGES, B answers READY =
  still unresolved). A reviewer the main session RESUMES with SendMessage after the NEEDS CHANGES counts as launched at
  the resume: the hook emits `helper_resume {task, agent_id, helper}` when a SendMessage from the main session (not from
  a helper, and not a refused user-only command) has `to` equal to the `agent_id` of a helper already paired in this
  session whose previous run has ENDED (`ended_ids`; a still-running helper, a helper sender or an unknown `to` changes
  nothing). It bumps `spawn_seq` and gives that agent the new `seq`, and, like a fresh launch, the current `version` and
  `task`. The resumed helper's next SubagentStart keeps its pairing (it never claims a pending launch) and re-opens its
  verdict capture; a stale SubagentStop replayed before that is not a verdict. Only verdicts arriving after the resume
  use the new seq; earlier ones are never resurrected. `derive` mirrors it: a `helper_resume` counts as a new
  launch of that `agent_id`, and a resumed helper's later verdict is not dropped as a duplicate. The hook keeps `last_verdict`, `last_verdict_seq` (the launch order of the reviewer), `nc_at` (how
  many helpers had been launched when the latest NEEDS CHANGES arrived; kept across a carry) and `spawn_seq`; `pending`
  and `agents` entries carry `seq`. `derive` mirrors it from the order of `helper_start` events (a helper's launch id, or
  its `agent_id` through `helper_paired`). Honest limits: a READY on an unrelated artifact, or from a reviewer that was
  told to answer READY, still counts. Also: a foreground reviewer's SubagentStop and PostToolUse can race around a
  resume (the first to land is the verdict); a SubagentStop replayed after the resumed run's SubagentStart is taken for
  the new run's verdict; resuming a non-reviewer only bumps `spawn_seq`.
  The main session's `version` counts only edits made in the main session (helpers edit in their own worktrees), so a
  count of NEEDS CHANGES with `version` 0 is NOT proof of an unresolved task. A task opened by a carry has no verdict
  yet, so it is unresolved and the next declaration carries again (the double-declaration escape stays closed) until a
  READY lands on it (the next declaration carries again because the carried task is `chained`).
  Only an exact duplicate within 60 s (accidental double call) is a no-op (logged as `ignored`), unless a `task:` token names a different Plan item than the open task's `plan_ref` (that opens a new task).
* A carry (any declaration, same type included, see "Declaring over an open failing review") carries `needs_changes`,
  `escalated` and `granted` into the new task and logs `refusal{guard: rework}` with the detail `carry-over, not a denial:
  budget carried over a new declaration (<n> NEEDS CHANGES)`; the new task's effective budget = min(old budget, new
  budget), stored in state (`derive` applies the same rule). The `work_type` event carries `carried: true`.
* **Rounds** (since 2026-10-26; only reviewer launches and verdicts count, versions do not). A NEEDS CHANGES verdict is a
  new round when it is the task's first NEEDS CHANGES, or its reviewer was launched AFTER the previous failing review of
  the task arrived (reviewer `seq` > `nc_at` as it stood before this verdict), or the reviewer's `seq` is unknown (the
  strict side). Several reviewers launched before a failing review arrives count once; a reviewer resumed with
  SendMessage counts as launched at the resume (`helper_resume`). The hook decides this when it records the verdict and
  writes it as `round: true|false` on the NEEDS_CHANGES `verdict` event (`apply_event` uses the field; a legacy event
  without it is decided by the same rule). State: `nc_rounds` (int, own rounds of both tiers, reset on a fresh open) and
  `carried_nc`; `nc_count = carried_nc + nc_rounds` (the total: done-lock, ledger stats and reports use it); `nc_at` =
  `spawn_seq` at every NEEDS CHANGES. **Two reviewer tiers (since 2026-11-03):** `senior` = the helper `senior-reviewer`,
  `routine` = every other reviewer. The round rule above is applied PER TIER: a NEEDS CHANGES is a new round for its
  tier when it is that tier's first (nothing carried, no own round of the tier), or its reviewer was launched after that
  tier's previous failing review arrived (`nc_at_t[tier]`, set to `spawn_seq` when a failing review of that tier arrives;
  an unknown tier, such as a late carry at the next open, sets both), or its `seq` is unknown. A routine and a senior
  reviewer launched together that both fail therefore count two rounds (one per tier); two routine reviewers launched
  together still count once. State adds `nc_rounds_t` (`{senior: n, routine: n}`, own rounds per tier, reset with
  `nc_rounds`) and `nc_at_t`. The tier is read from the `helper` field the `verdict` event already carries (no new
  field; a legacy line is treated the same way by helper name). `derive` keeps its total (`rounds.needs_changes`, `own`, `carried`: stats and reports read them) and also counts
  own rounds per tier from the `helper` field of the verdicts that count as a round (see §1.7); a NEEDS_CHANGES verdict without the field (a legacy stream) counts
  one round per distinct failing `version`, so historic numbers do not change. On such a legacy stream (no `round` field)
  the hook's replay (`rebuild_state`) can count a routine and a senior failure on the same version as two rounds, while
  `derive` counts one per version; the totals in history do not change.
* **Late verdicts** (since 2026-10-26). A NEEDS_CHANGES or ESCALATE verdict whose task is not the open task (its reviewer
  was launched for an earlier task) or that arrives when no task is open is never lost: it counts on the open task as a
  carried round (a late NEEDS CHANGES always counts +1, whatever `nc_at` was: `carried_nc += 1`, `nc_at = spawn_seq` so only a reviewer launched after it can resolve, `chained`
  true; ESCALATE sets `escalated`). With no task open it is added to the state counters `late_nc` / `late_esc`, applied the
  same way to the next task that opens (fresh, carried or implicit) and then reset. The hook records the decision on the verdict
  event as `counted_on: <open task id>` or `"next"`; `round` is not set. `derive` mirrors it: a verdict with `counted_on` adds a
  carried round (and `nc_at`, escalation) to that task or to the next opened one, and is not an own round of its launch task.
  The entry in the launch task's `verdicts` list carries `late: true` and never becomes that task's `final_verdict`. A late
  verdict before any task exists in the session also applies to the first task opened. A late READY changes nothing. Events without `counted_on` derive as before.
* **Closing** (guard `done_lock`, §6.5): `: team-done` is refused while the task has an open failing review, whatever the
  version or budget: `(nc_count > 0 and not resolved) or escalated`.
* **Declaring over an open failing review** (`nc_count > 0` and the open task is not resolved). If the task is escalated
  or `chained` (spent or not), the declaration CARRIES exactly as in the carry bullet above. Otherwise the hook emits
  `task_abandoned {task, needs_changes, granted}` for the old task and opens the new task FRESH (own budget, `granted` 0,
  no `carried` flag). Any abandon chains: the task opened next is `chained` (`chain_next`). A task opened by a carry is
  `chained`. A fresh open over a task with no open failing review opens fresh as before, and is `chained` when the old
  task (still open, or closed with `team-done`) was `chained` and has not passed review with a change: the chain ends
  only on a passing review of a task that changed something, i.e. `task_resolved` (READY from a reviewer launched after
  its latest failing review) AND `version > 0` (main-session or helper edit events); a READY on a task with no edits does
  not end it. It survives any declaration, an empty one included. An escalated task with no failing review carries as
  before. `derive` mirrors this through the hook's `carried` flag: `task_abandoned` sets status `abandoned` and the next
  task starts fresh (`own 0, carried 0`); a `work_type` with `carried: true` carries. `/grant-rework` is plain (§6.4):
  `granted += n` on the current task, `escalated` cleared. The files a task edited are never locked and shell commands
  are never parsed. The hook can't tell whether new work is really new: a session gets one fresh budget per chain, and a
  chain ends only on a passing review of a task that changed something. Every abandon is recorded and shown on the Ledger
  and in the weekly report.
* A non-exempt edit with no open task opens an implicit task of type `undeclared`
  (`needs_check: true`, `default_budget`).
* Playbook names = those listed in some area's `playbooks` or in `workflows.yaml` `playbooks:`; only
  those open a `playbook` task; the same command within 10 s opens one task, not two.
* `: team-*` commands issued inside a helper (`agent_id` present) are ignored (`ignored` event).

### 1.4 Per-session state cache (`state/<sid>.json`), hooks only

```json
{"sid": "...", "task": "abcd1234-2", "n": 2, "type": "coding", "area": "atlas",
 "version": 7, "last_verified": 5, "needs_changes": 1, "escalated": false, "granted": 0,
 "pending": {"<tuid or agent_id>": {"helper": "reviewer", "version": 6}},

```

A cache only: if missing or unreadable, the hook rebuilds it by scanning back day files to the one

### 1.5 Cost capture

At every `Stop` and `SessionEnd`, read the session transcript (`transcript_path`) and each helper
transcript (`<transcript dir>/<sid>/subagents/agent-<id>.jsonl`) from the stored byte offset to EOF.
**Claude Code writes one line per content block, each repeating the message's `usage`** (measured:
3,577 usage lines for 968 messages), so: dedupe by `(message.id, requestId)`, per message take the
max of each field (`input_tokens`, `output_tokens`, `cache_read_input_tokens`,
`cache_creation_input_tokens`); keep in `offsets-<sid>.json`, per transcript, the last 200 message ids
with the amounts already emitted and emit only deltas (a message's lines can straddle a Stop). Skip
`isSidechain: true` lines in the main transcript. Helper scope = the `agent-<id>` in the file name;
helper type from the sibling `.meta.json` if present, else the pairing map. Write one `cost` event
per (scope, model) with a non-zero delta, then store the new offsets. When the pass sees a
`custom-title` entry newer than the last one recorded, the `cost` event carries `title` (that is the
ledger's durable source of the session's sidebar title). `weighted` = `(in + out) × weight(model, in)` with the
weights of `dashboard/usage.py:model_weight` (copied into the hook config, `hooks/atlas_config.json`,
so the hook never imports the repo). Weights (Sonnet = 1.0): haiku-5 0.05 (0.25 above 100k prompt tokens), haiku 0.5, opus 2.0, sonnet 1.0, **fable 4.0** (since go-live, see the build log; price ratio, the `advisor` helper's model); an unknown model weighs 1.0 and shows as `sonnet`. A transcript that shrank resets its offset to 0. Lines that do
not parse are skipped. Cost reading must not block the Stop beyond 2 s: stop reading and keep the
offset where it got to.

### 1.6 v1 import (`tools/import_v1_ledger.py`)

Reads `<repo>\ledger\events.jsonl` (READ-ONLY; path overridable by `--src`), writes
`ledger/v1/events.jsonl` (overwritten on each run, idempotent): each original line becomes
`{"v": 1, "src": "v1", ...}` keeping **only an allowlist** of fields: `t, ev, job, project, lane,
phase, to, was, status, verdict, plan_task, branch, commit, tokens, cache_read, cache_write,
cache_creation, fresh, input, output, model, effort, duration_s, attempt, rework, findings, result,
kind, which, action, pass, estimate, type` (everything else, notably `task, notes, q, note, why,
error, diffstat, question, answer`, is dropped). Verdicts map `commit-ready → READY`,
`needs-changes → NEEDS_CHANGES`, `escalate → ESCALATE`. A v1 task's title = `plan_task`, else the job
id. Reports counts per kept/dropped field.

### 1.7 Task records (derived on read: `cockpit/ledger2/derive.py`)

A task runs from its opening event to the first of: its `task_done` (status `done`), the next opening
event in the same session (`switched`), a `task_abandoned` for it (`abandoned`, since 2026-10-26: a task with an open failing review a
new declaration left behind; the next task opens fresh, with no carry), `session_end` (`ended`), or nothing
yet (`open`). v1 jobs
become tasks with `src: "v1"`, `type: "coding"`, area from the project (`areas.yaml` `projects`),
crew from their phases, verdicts from `review` events, status `done` when merged.

`duration_s` is the task's **active time**, not its wall-clock span: the union of (a) every helper interval
(`helper_start` or `helper_resume` to the matching `helper_end`, paired by `tuid`/`agent_id`; a helper with no end runs to
the task end) and (b) every gap between two consecutive events of the task (task open and task end included) of at most
`IDLE_GAP_S` = 15 minutes (`derive.py`). Longer gaps outside a helper interval count zero. `span_s` is the old wall-clock
value (`started` to `ended`, or to the last event while open). v1 imported tasks (`src: "v1"`) have no event detail:
`duration_s` = `span_s`. Carry-over notices (a `refusal` with `guard: "rework"` and a detail starting `carry-over`) carry
`notice: true` in the task's `refusals`.

```json
{
  "id": "abcd1234-2", "src": "v2", "sid": "...", "session_title": "Atlas v2 build",
  "area": "atlas", "type": "coding", "playbook": null, "plan_ref": "evt_0a1b2c3d", "plan_auto": false, "auto": false,
  "started": "...", "ended": "...", "duration_s": 5400, "span_s": 7200, "status": "done",
  "crew": ["implementer", "test-runner", "reviewer"],
  "helpers": [{"helper": "implementer", "count": 2, "labels": ["Build ledger store"]}],
  "rounds": {"needs_changes": 1, "budget": 2, "granted": 0, "left": 1, "own": 1, "carried": 0},
  "verdicts": [{"t": "...", "helper": "reviewer", "verdict": "NEEDS_CHANGES", "version": 4, "findings": 3}],
  "final_verdict": "READY", "checked": true, "unverified_flag": false,
  "caught": 3, "edits": 9, "refusals": [{"guard": "rework", "would": true}],
  "cost": {"weighted": 1234567, "by_model": {"claude-opus-5-5": {"in": 0, "out": 0, "cache_read": 0, "cache_write": 0, "weighted": 0}},
           "by_helper": {"chief": 800000, "implementer": 300000}},
  "summary": {"goal": "...", "produced": "...", "decisions": "...", "open": "...", "review_min": 20}
}
```

* Per-tier fields (since 2026-11-03): `rounds.own_routine` and `rounds.own_senior` = own rounds by tier (`senior-reviewer` is
  `senior`, every other reviewer `routine`; a legacy verdict without `round` is assigned to its helper's tier by the same
  per-version rule); `rounds.used` = `carried + max(own_routine, own_senior)`, and `rounds.left` = `max(0, budget +
  granted - used)` (the hook's rule, §6.3), so a task with routine 2 and senior 1 under budget 2 shows `left` 0 while
  `needs_changes` is 3. The bypass report's "N of M rework used" uses `used`.
* `rounds.own` = this task's own NEEDS CHANGES rounds, `rounds.carried` = rounds carried over from the previous unresolved
  task in the session (`needs_changes` = carried + own; `left`: see the per-tier fields above). Own rounds follow
  "Rounds" in §1.2: a NEEDS_CHANGES verdict with a `round` field counts when it is true; one without it (legacy) counts one
  round per distinct failing `version`. An `abandoned` task keeps its own rounds; the next task starts at `own 0, carried 0`
  (or carries when its `work_type` has `carried: true`). Legacy events are still read: `rework_recalled` gives the task `carried += nc` (also
  `nc_at` = the spawn count), budget = min(current, the `from_task`'s) and `granted += the from_task's`; a `rework_granted`
  with `for_task` counts on that task when it exists in the session, else on the current task. A stream without
  `task_abandoned` derives exactly as before. Anything that sums or buckets rounds per task (the stats `rounds_hist`, the
  weekly report) uses `own`, so a carried count is never counted twice.
  The weekly report's "Review and gates" section (`tools/weekly_report.py`) carries one more signal (since 2026-11-03,
  JSON `review.senior_after_routine_ready`: list of task ids): tasks closed in the week where a `senior-reviewer` returned
  NEEDS_CHANGES after another reviewer had returned READY on the same task, read off the task's `verdicts` (late verdicts
  excluded); the line shows the count and the ids.
  Right after the rounds line it prints "Rework per closed task" (JSON `review.rework_concentration`: `rounds`, `closed_tasks`,
  `per_task`, `top_session`, `top_rounds`, `top_pct`, `top_tasks`, `per_task_without_top`): rounds divided by closed tasks, the
  session (task id up to the last `-`) holding the most rounds with its share, and the rate without that session; same closed
  tasks and same `own` round count as the rounds line; `n/a` and null fields when there are no rounds. The "Waste signals"
  section adds three lines, all derived from existing events (no new hook event; JSON `waste`): `main_edit_run`
  (`{max, max_task, stop, tasks_above_stop}`: per task the longest run of main-session `edit` events, no `agent_id`, between
  `implementer`/`drafter` `helper_start` launches, the task start counting as a reset; memory files emit no `edit`; only tasks whose type's crew in `workflows.yaml` has an `implementer` or `drafter` are counted, as in the hook's stop: `undeclared` counts, and a `playbook` uses its `playbook_crews` entry by the `playbook` event's `cmd`, a builder being assumed when the command is unknown),
  `edit_limit_refusals` (`{enforced, would}`: `refusal` events with guard `edit_limit`, the 6-edit stop) and
  `test_runner_reminders` (`{total, tasks}`: the section 6.9a reminder emits no event, so it is derived: on a `coding` task, a
  `reviewer` or `senior-reviewer` `helper_start` after an `implementer` `helper_end` with no `test-runner` `helper_start` since; counted per reviewer launch, like the hook, which is stateless).
  The report's weighted-usage section also carries a cost split (JSON `usage_weighted`): `by_helper_area_type` = list of
  `{helper, area, type, weighted}` summed over the week's closed tasks from `cost.by_helper` (weighted > 0 only, sorted
  descending; area and type normalised as in the by-area and by-type tables: `unassigned`, `undeclared`), and
  `senior_top_tasks` = up to 5 `{id, area, type, weighted}` with the highest `senior-reviewer` cost (> 0), descending, ids
  only (no titles). The Markdown shows both after "By helper" ("By helper, area and type", "Most expensive senior-reviewer
  tasks"); an empty list renders `_none_`.
* `title` = the task's name: summary `goal`, else the first helper's first label (the description the main session gave it),
  else the session title, else null. The tasks endpoints (§5.2) replace it with `plan_title` when that resolves, so the field
  is the one name to show; `session_title` stays for a muted second line. A v1 job that never finished is `ended`
  (v1 is retired), with `ended` = its last event.
* `plan_ref` = the opening event's `plan_ref` (null when none); `plan_auto` = the opening event's `plan_auto` (true when the link was inferred, false otherwise). The tasks endpoints (§5.2) add `plan_title` to EVERY task: the
  Plan item's current title when the ref resolves (read-only, via `cockpit/plan/refs.py`, finished project-plan tasks included), else null.
  The Ledger tasks table shows a linked task as a muted "Plan:" prefix plus that title (its own name as the hover hint), so cost per Plan item is visible.
* A task is **resolved** when its latest verdict is a READY covering the latest main-session version (see the task-opening
  rules); a task with an open failing review is abandoned or carried by the next declaration (§1.2; a carried task has no verdict yet,
  so it cannot be re-declared into a fresh budget). A task that got NEEDS CHANGES and then a READY is resolved even when the
  main session never edited (`version` 0); main-session edits after the READY make it unresolved again, and so does a
  READY from a reviewer launched before the latest NEEDS CHANGES arrived.
* `checked` = the final version has a READY verdict (or an `ok` check, §1.2) at that version.
* `unverified_flag` = type with `needs_check: true` (incl. `undeclared`), status `done`, `switched`
  or `ended`, edits > 0 and not `checked` (the Ledger's safety net).
* Verdicts and helper ends are deduplicated by `agent_id`.
* `caught` = sum of `findings` over NEEDS_CHANGES verdicts.
* `auto` = the session has an `auto` event (its first command `: team-auto <marker>`, §7) whose
  marker exists in `ledger/auto/`.
* Cost of a task = `cost` events of the session between its start and end, by `scope`; helper cost
  attributes the helper's `agent_id` to its `helper` type.

## 2. The types of work

`workflows.yaml` (root) is the one source: label, crew, `budget`, `rung`, `needs_check`, `move`
(the ladder's "what would move it"), plus `builders`, `reviewers`, `default_budget`, `aliases`,
`playbooks` (a plain list of names, which is all the hooks read) and `playbook_crews` (per playbook:
`crew: [helper ids]`, optional `budget` (omitted = inherits `types.playbook.budget`), optional
`per_task: true` = the playbook starts other work, so the real crew and budget are the task's type;
`crew` then lists only the helpers the skill names itself). Each crew is read off the playbook's own
skill text, never invented; `test_playbook_crews_cover_repo_skills` checks every repo-owned skill
(`skills/<name>/SKILL.md`) against it. The hooks read `workflows.yaml` and `areas.yaml` from the repo paths named in
`atlas_config.json` (`workflows_file`, `areas_file`), cached by mtime, falling back to the installed
JSON copies if the YAML is missing or does not parse, so a one-line edit reaches the hooks without a
reinstall. An unknown declared type is recorded as written and gets `default_budget`,
`needs_check: true`.

**Bash edits (documented gap):** edits made through shell commands (`sed -i`, redirects, scripts,
`git apply`) do not bump the version and are not stopped by the quick-question lock. Accepted for
v2: helpers edit through Edit/Write, and the reviewer checks the diff, not the event count.

## 3. The areas file

`areas.yaml` (root), format documented in the file itself: `areas: [{id, name, color, folders?,
playbooks?, projects?, match?, group?, attention?, attention_fixed?, short?, archived?}]`. The areas of this copy are the example set in `areas.yaml`, in file order (the order the
colour-blind check passed).
Parallel planning keys (2026-10-11), all optional and checked by `tools/check_look.py`: `attention: shared|full` (absent =
full; a shared event may run in parallel with other shared events, a full one overlaps nothing), `attention_fixed: true`
(an event cannot override the area's attention), `short: <2-5 capitals A-Z>` (the compact label on the Plan). Values: the example set shows each combination.
`archived: true` (since 2026-10-20, bool, absent = false, checked by `check_look.py`) retires an area without deleting it: the entry
stays loaded and `GET /api/v2/areas` and the Plan `areas` list carry `archived` (bool) for every area, so past events, tasks and
ledger rows keep their name, short label and colour. An archived area is hidden from every picker and list that offers areas for
NEW work (event form, memo form, legend entries nobody uses; screens that show history, such as the Ledger, keep it), is skipped by
the `match` rules of §5.3, and the Plan refuses new items in it (§5.3 `plan/event`, `plan/task`). `folders`, `playbooks` and `projects`

## 5. The HTTP API (v2)

The v2 server is the existing `cockpit/server.py` with a seam (Wave 0): requests under `/api/v2/` go
to `cockpit/api_v2.py`, which routes by prefix to one lane module; static requests go to
`cockpit/web2_static.py` (served from `cockpit/web2/`) when the path is not `/api/…` and not under
`/v1/` (the old front end was removed on 2026-10-10 with the v1 wrap-up). Each lane module exposes:

```python
def get(path: str, query: dict[str, str]) -> tuple[int, dict] | None: ...   # None = not mine
def post(path: str, body: dict) -> tuple[int, dict] | None: ...
```

Routing is by prefix: `/api/v2/ledger/` → `ledger2.api`, `/api/v2/plan` → `plan.api`, everything
else → `shell_api`; each call is wrapped so one lane's exception is a 500 for that path only. A POST
body that is not valid JSON or not an object → `400 {"ok": false, "error": "body must be a JSON
object"}` before any lane sees it.
**Branch-server safety:** when `ATLAS_BRANCH_SERVER=1` (the branch server sets it with `ATLAS_NO_INBOX_SYNC=1`), server.py answers
`403 {"ok": false, "error": "read-only on the branch server"}` to every v1 write: POST
`/api/schedule/*`, `/api/plan/*` (v1), `/api/planner*`,
`/api/job/*`, `/api/dispatch*`, `/api/procedure`, `/api/monitor/*`, `/api/brain/*`.
`web2_static.serve(route, if_none_match)`: `/` → `index.html`; the path is resolved and must be
inside `cockpit/web2` (else 404); once `cockpit/web2/index.html` exists, a missing file is
`(404, …)`, never `None` (no silent fallback to a v1 file of the same name).
Errors: 400 bad input, 404 unknown id, 409 version conflict (§5.3), 500 unexpected (logged).
Every handler is fast (< 200 ms on today's data); anything slow is computed in a background thread
and served from a cache (ledger stats).

**Done sessions (2026-10-12, amended 2026-10-13, 2026-10-29).** The orchestrator closes a finished task with the no-op shell command `: team-done` (never from a helper). `hooks/team_events.py` matches it like the Atlas hook does: on the FIRST line of the command (capped at 200 characters), `^\s*:\s*team-done\b`, anything may follow (`: team-done now` and a `: team-done` followed by more lines count; `: team-doner` does not). It logs `{ev: "TeamDone", ts, sid, cwd}` and nothing else at PreToolUse, in the team-live log next to `WorkType`. In `teamlive`, a session is `done` when a main-session `TeamDone` (not `in_agent`) comes after its current task's opener (the latest `WorkType` or playbook command, the same anchor as the current-task window) AND no real new work comes after the last such `TeamDone`: a main-session (not `in_agent`) `PreToolUse` with `tool` `Agent` (a helper launch) or `Skill`. A plain `UserPromptSubmit` does not clear `done`: a follow-up turn with no helper launch, skill or new declaration stays done; new work in the same session is declared with a new `: team-type` (or launches a helper or a skill), which re-opens it (it is then working or waiting as usual) until the next `: team-done`. A newer opener also re-opens it, and a session with no opener is never `done`. `GET /api/v2/team` sessions carry `done` (bool). `waiting` is true only while the session is idle, the last main-session event is a Stop within 2 h AND the session is not `done`; `/api/v2/attention` follows `waiting`, so a done session reads `idle` there. `done` changes nothing else (`status`, hiding, timelines). The Team row shows a quiet `done` label where `waiting` would show. Known accepted limit: `TeamDone` is logged at PreToolUse, so in enforce mode a team-done refused by the done-lock still shows done until the next declaration, playbook, helper launch (`Agent`) or `Skill` call; the ledger stays the record.

**Live helpers (2026-10-10).** A session is `working` when its main conversation is working OR at least one of its
helpers is live, background (`run_in_background`) or foreground alike. A helper is live when the event log has its
`SubagentStart` and no matching stop AND its own transcript (`<project folder>/<session id>/subagents/agent-<id>.jsonl`,
next to the session transcript) was written within `HELPER_FRESH` = 8 minutes of now. Measured helper transcripts
(44k consecutive records) show a median gap of 0.6 s and a 99th percentile of 57 s, but the full test suite runs about
5 minutes inside a single Bash call with no transcript write meanwhile, so the window is 8 minutes: a working
test-runner is not shown as gone, and a lost `SubagentStop` leaves a ghost for at most 8 minutes. A stale transcript closes the helper
at its last write. The transcript is the evidence because the hook log is silent while a helper edits and reads (only
Agent, Skill and `: team-*` calls are logged), so the older "no event for 10 minutes means gone" rule wrongly closed busy
background helpers and the session read "waiting" while they worked. When no transcript can be found the event-log rules
apply unchanged. When the session is working only because of helpers (`via_helpers`), the Team row reads
"working · N helper(s) in the background" (or "running" when any is foreground) with each live helper's creature
name and task label, the helper pipeline shows it as working, and `/api/v2/attention` counts the session as working,
not waiting. When the last helper finishes and the conversation is idle, the session returns to waiting or idle.

**Helper runs for the Team chart (2026-11-16, additive).** Each session in `GET /api/v2/team` also carries
`helpers`: one entry per helper run, ordered by start, `{agent_id, agent, type, n, label, bg, start, stop, start_h, stop_h,
running, resumed, verdict, task}`. `agent` is the display id (the key of `T` in `team-creatures.js`, as in `steps`), `type` the
agent type as launched, `n` the 1-based instance number per `agent` within the session (by start, counted before the cap),

task and type); `helpers_total` is the full count. `span: {start_h, end_h}` is the orchestrator's lifeline: the session's first event

mtime and size); any error leaves it null and never fails the payload. `steps` and every other field are unchanged.

*Task groups (2026-11-16, additive).* Each helper also carries `task`: the ledger task id it belongs to, or null. It is the
LAUNCH task: `helper_paired.tuid` is matched to the `helper_start` with that `tuid` and its `task` is used (so a helper
paired after a new `: team-type` declaration stays in the group it was launched in); when `tuid` is null or unmatched the

Titles are never rewritten automatically. Events may carry `task_of: <task id>` (additive, returned in `events`).
An expanded event carries `done: true` when the event has `done: true` (single) or the occurrence date is in its
`done_on` list (series); the key is absent otherwise. The mark is manual only: nothing sets it automatically, it
feeds no statistic and is independent of task states in `tasks.yaml`.
**Day window 07:00 to 22:00** (screen review 2026-10-09): a timed event outside it is refused (400
`... is outside the 07:00-22:00 day`) on create, move and occurrence retime; only when the day/time of the event
is new or changed, so legacy events outside the window stay editable. **All-day rule:** an all-day event is
never busy-checked against the day's other events; once a day has an all-day event (a recurring occurrence
counts, a skipped one does not), a NEW timed or all-day event on that day, or an event moved onto it, is refused
(400 `can't save 'X': <day> already has the all-day event 'Y'`); events already there stay as they are.
**Parallel planning (2026-10-11).** Up to 3 Claude Code sessions may run at once, so the Plan allows up to
`MAX_PARALLEL = 3` overlapping *shared* work blocks, while *full* blocks (training, personal life) overlap nothing.
*Effective attention* of an event: the area's value when the area has `attention_fixed`; else the event's own `attention`
(`shared|full`, stored in `schedule.yaml` only when set explicitly; anything else is 400); else the area's `attention`; else
(no area resolved) `full`. The area is resolved exactly as for the read path (explicit area, else title prefix, else keyword).
GET events carry `attention` (effective) and `attention_source` (`fixed|event|area|default`); GET areas carry `attention`,
`attention_fixed`, `short`. Sending `attention` on an event whose effective area is fixed to another value is 400
`can't save 'X': <Area name> is always full`.
**The guard** replaces the busy-overlap rule between timed events (window rule, all-day rule, availability blocks,
`full_days` and placements keep their behaviour; the latter three keep the schedmath reason text). For a timed busy event
being created, moved or retimed, against every other timed busy event occurrence of that day (recurrences expanded, overrides
and skips applied, itself excluded, `busy: false` and all-day events ignored):
a FULL event overlapping any other event is 400 `can't save 'X': overlaps 'Y' (HH:MM-HH:MM); 'X' needs full attention`;
a SHARED event overlapping a FULL event is 400 `can't save 'X': overlaps 'Y' (HH:MM-HH:MM), which needs full attention`, and
if at any instant inside its slot the shared events (itself included) would exceed `MAX_PARALLEL` it is 400
`can't save 'X': 3 sessions already run in parallel HH:MM-HH:MM` (the merged stretch where 3 shared events already run).
The verb in the prefix is `save`, `move` or `retime ... on <day>` as before. The guard runs only when day/start/end/busy or
the effective attention changed, so a notes-only edit on legacy overlapping data is never refused. It applies to event upsert,
`event/move` (occurrence overrides and cross-day occurrence moves included), `task/place` "me" and `review/schedule`.
`MAX_PARALLEL` lives in `cockpit/plan/model.py` only.

**Event write semantics:** upsert = merge onto the stored event; fields not in the request
(`skips`, `overrides`, `busy`, `remind`, `location`, anything unknown) are kept; a field sent as
`null` is removed; `area` must be an id in `areas.yaml` (else 400). Moving one occurrence: same day →
`overrides[date]`; different day → `skips += occurrence` plus a new single event (same title, area,
type, `from_series: <id>`, plus `done: true` when that occurrence was marked done, whose date then leaves `done_on`),
in one locked write. `done` / `done_on` are kept by an upsert like any other unknown field. Collisions with busy time → 400 with v1's reason text
(the v1 guard is kept). Hand-written unquoted times (`10:00` loaded as an int) are normalised to
`"HH:MM"` on read.

Answer: `{ok, version, changed: {...the object as stored...}}`. **Versions and conflicts:**
`plan-version.json` = `{version, objects: {key: {v, sha}}}`, keys `evt:<id>`, `plc:<session>`,
`blk:<id>`, `dl:<id>` (deadlines, §5.3a), `task:<id>`, `rv:<task_id>`. On every load, an object whose content hash changed (an
edit from outside: a session, a hand edit, the v1 cockpit) is bumped to `version + 1`. A write whose
object has `v > base` → `409 {ok: false, error, current: {...}, version}`; `base` missing → 400;
writes to other objects never conflict. **Saves:** one process-wide `threading.Lock` + an OS lock on
`<file>.lock` (`LK_NBLCK`, 20 × 50 ms, else 503) around read-modify-write; write `<file>.tmp` then
`os.replace`, retried 10 × 50 ms on `PermissionError`, then 503 with nothing lost. **If the file does
not parse, refuse the write (500, nothing written)** (v1's `_load_events_list` returns `[]` on a parse
error, and a save then wipes every event: never copy that). Sections other than the one written stay
byte-identical; every section boundary backs up over the comment and blank lines above the next key
(as v1 `_placements_region` does); a test runs a write on a copy of the real `schedule.yaml` and
diffs the other sections. `version` is bumped on every successful write; the client ignores any
response whose `version` is lower than one it has seen. The Plan endpoint never calls
`state.snapshot()` and never reads transcripts.

### 5.3a Deadlines and the Brief read (`cockpit/plan/brief.py`, `cockpit/plan/api.py`)

A deadline is a date to meet or a follow-up to chase. It has no time, takes part in no collision check and never
blocks anything. It lives in a top-level `deadlines:` list of `schedule.yaml`, written only by the plan engine
(through the same section splice as `events:`), versioned under the key `dl:<id>` (`model.schedule_objects`
and `SCHED_PREFIXES`), so stale-base detection (409) covers it. Every other reader of `schedule.yaml` ignores the section.

| Field | Meaning |
| --- | --- |
| `id` | `dl_<8 hex>`; a new one is made when absent on upsert |
| `title` | what is due |
| `day` | `YYYY-MM-DD`: the due day (follow-up: the day to chase); for a series, the first occurrence |
| `area` | areas.yaml id, optional; same resolution and archived rule as events (400 `area archived: <id>` for a new item) |
| `notes` | optional text |
| `kind` | `deadline` (default) or `follow-up` |
| `remind_days` | int 0 to 366 (400 otherwise; clamped to 366 when read), days before the due day when the item enters "Do not miss"; default 14 for `deadline`, 0 for `follow-up` |
| `priority` | `normal` (default) or `high` |
| `recur` | optional `{freq: daily\|weekly\|monthly, interval?, until?, count?}`; a monthly series may also carry `weekday: mon..sun` and `week: "last"\|1..4` (that weekday in that week of the month, for example the last Saturday). The record's `day` must itself match the weekday rule (400 otherwise). A monthly rule without `weekday` is anchored on `day`, and an anchor day above 28 is 400 `can't save '<title>': monthly anchor day must be 28 or less`; that rule does not apply to weekday rules |
| `done` | bool, single item only |
| `done_on`, `skips` | sorted ISO days, series only; keys are the ORIGINAL occurrence days |
| `overrides` | series only: `{original occurrence day: {day}}`, moves one occurrence |

Recurrence reuses `schedmath._occurs_on`, which also implements the monthly weekday rule shared with events (§5.3); `brief.occurs_on` delegates to it.

**Writes** (all `POST`, JSON, same `base`, version and 409 rules as every plan write; one locked read-modify-write each):

| Path | Body (besides `base`) | Effect |
| --- | --- | --- |
| `/api/v2/plan/deadline` | `{deadline: {id?, title, day, area?, kind?, remind_days?, priority?, recur?, notes?}}` | upsert: merges onto the stored item, fields already stored are kept, a field sent as `null` is removed, a bad value is 400, and so is a request field outside the table above (400 `unknown field: <name>`). An `id` that does not exist is 404 |
| `/api/v2/plan/deadline/done` | `{id, occurrence_key?}` | single: `done: true`. Series: the key is added to `done_on` (idempotent) |
| `/api/v2/plan/deadline/move` | `{id, to_day, occurrence_key?}` | single: `day` changes. Series: `overrides[occurrence_key] = {day: to_day}` (moving back to the key itself removes the override) |
| `/api/v2/plan/deadline/delete` | `{id, occurrence_key?}` | without the key: the item or the whole series is removed. With the key (series): that occurrence is added to `skips` |

For a series, `done` and `move` require `occurrence_key` and `occurrence_key` must be a real, unskipped occurrence (400
otherwise); sending `occurrence_key` for a one-off item is 400. `done_on`, `skips` and `overrides` are never set through
the upsert (400). Answer `{ok, version, changed}`; unknown id 404, stale base 409, no plan file 503.

**Read:** `GET /api/v2/plan/brief?day=YYYY-MM-DD` (default today; 400 on a bad day). Read-only (writes no version, no file). `version` is the stored Plan version (the value `GET /api/v2/plan` returns once outside edits are detected), the `base` a write needs.

```json
{"ok": true, "day": "2026-11-16", "version": 42,
 "do_not_miss": [{"id": "dl_…", "occurrence_key": "2026-12-18", "day": "2026-12-18", "title": "…", "area": "admin",
                  "kind": "deadline", "priority": "high", "days_left": 32, "days_text": "in 32 days", "overdue": false,
                  "notes": null, "recurring": false, "group": "overdue|today|high|window"}],
 "act": [], "act_status": {},
 "today": [{"type": "event|block|placement", "id": "…", "occurrence": null, "title": "…", "day": "2026-11-16",
            "start": "10:00", "end": "11:00", "area": "pers", "done": false, "can_mark_done": true}],
 "next": [{"...same as do_not_miss": "", "group": "next", "week": "2026-11-16"}],
 "counts": {"do_not_miss": 3, "act": 0, "today": 5, "next": 7, "overdue": 0, "deadlines_30": 7,
            "events_today": 4, "events_done": 2, "skipped": 0}}
```

* "Do not miss" is ordered by group (overdue, due today, high priority in window, in window), then by `day`, then title.
  An item shows once, in the first group it fits. Everything is evaluated on the displayed `day` (after overrides). A series
  contributes at most two entries: its latest not-done occurrence displayed before today (overdue) and its next not-done
  occurrence displayed today or later. "Window" means `day - remind_days <= today`.
* "Next 30 days" holds the remaining not-done items displayed from tomorrow to today + 30, ordered by day, each with the
  `week` (Monday) it falls in. A one-off item overdue stays overdue until done.
* `today` holds every Plan block of the day, all-day items first, then by start: events (`can_mark_done: true`, `occurrence`
  set for a recurring event, the key the `event/done` write needs), work blocks and placements (`can_mark_done: false`).
* `counts.deadlines_30` = not-done entries of both blocks with displayed day from today to today + 30 (overdue excluded).
  `events_today` / `events_done` count events only. `counts.skipped` counts deadline records that could not be read (a hand-edit
  gone wrong: bad id, day or field types): they are left out, nothing else of them is shown, the rest of the Brief renders.
  `day` outside 1970-01-01 to 9998-12-31 is 400.
* `days_text`: "today", "in 1 day", "in N days", "1 day overdue", "N days overdue".
* `act` and `act_status` come from the guarded gatherer `cockpit/plan/brief_act.py`, run after the plan file locks are released.
  `act` is a list of `{source, kind, text, count, date, priority, open}` (`source` and `open` are `inbox`, `finance` or `team`;
  `priority` `high` or `normal`; high first, then the kind order below). `act_status` is `{inbox, finance, team}`, each `ok` or
  `unavailable`; a source is unavailable only when its database cannot be opened (or, for team, the ledger or live team state
  cannot be read), and then contributes one line ("Inbox unavailable", "Finance unavailable", "Team unavailable"). Lines hold
  counts, categories and dates only: no sender, subject, snippet, amount or account name. In a build without the inbox or finance
  package that source is omitted silently (no line, no `act_status` entry).
  Both databases are opened read-only (`mode=ro`) and nothing is fetched. Paths: `ATLAS_FINANCE_DB`, `ATLAS_INBOX_DB` (env
  overrides; default the finance package's `finance.db` and the inbox home's `inbox.db`).
  Kinds: inbox `act_mails`, `act_dated`, `auth_expired` (the persisted sync flag), `to_classify`; team `waiting_sessions`.
  Private sources may add lines; the public build has none. Each kind is guarded on its own: a failing kind drops its line only.
* Team line: "N sessions waiting: <title>, <title>, <title>" (up to 3, then "and N more"). A session counts as waiting while it has
  stopped and its task is still open; it leaves once the task is finished, the session is archived, or 4 days after its last
  activity (older ones are treated as orphaned). Sessions
  working now and automatic sessions are not counted. Priority high when any waited more than 24 hours. Join: ledger task records
  with status `open` against the live team state (working or done sessions left out); a session missing from the live state
  has stopped.

**Chat input** (`tools/plan_day.py`): ops `deadline` (add, or edit when `id` is given), `deadline-done`, `deadline-move`,
`deadline-delete` (an id may be written `dl_xxxxxxxx@YYYY-MM-DD`, the occurrence key), and `plan_day.py deadlines` which
lists the Brief's deadline entries. Same conventions as the other ops. Example: `{"op":"deadline","title":"Monthly review, last Saturday",
"day":"2026-11-28","recur":{"freq":"monthly","weekday":"sat","week":"last"}}`.

### 6.2 Verdict capture
The `advisor` helper is not in `reviewers`: its output is never captured as a verdict, whatever its first line says, and it adds no rework round (§1.2).
Helpers in this environment end with the `SubagentHandback` tool, so the final text may not be in
`last_assistant_message`. Sources, first that yields a match wins, **one verdict per `agent_id`**
(the hook records captured ids in state and ignores a second capture; `derive` dedupes too):
1. PreToolUse `SubagentHandback` fired inside a reviewer (`agent_type` in `reviewers`): the first
   line of `tool_input.message`;
2. SubagentStop of a reviewer: the first non-empty line of `last_assistant_message`;
3. a foreground PostToolUse Agent of a reviewer that has really finished: the first line of `tool_response.content[].text`. An async acknowledgement (`tool_response.status` `async_launched`, or `isAsync`) is never a verdict, and neither is a PostToolUse while the paired agent has not ended.
Match, case-insensitive: `^\W*(?:verdict\W*)?(READY|NEEDS[ _-]CHANGES|ESCALATE(?: TO OPERATOR)?)\b`
(`ESCALATE TO OPERATOR` = ESCALATE). No match → no verdict (a `helper_end` only). `findings` = count of
lines after the first that start with `-`, `*` or `<digit>.`

**Pairing a reviewer to its version:** PreToolUse Agent stores a pending entry `{tuid, helper,
version}`. SubagentStart (carries `agent_id`, `agent_type`) pairs with the **oldest unclaimed pending
entry of the same helper type** (the rule `teamlive` already uses, commit cc25e80) and logs
`helper_paired`. If the pairing is ambiguous, use the lowest pending version of that type: that can
cause a false send-back, never a false pass. An `agent_id` already paired never claims a pending entry (a resumed
helper logs `helper_paired` with `tuid: null` and keeps its record). PostToolUse Agent releases the pending entry only when the launch has finished (no async acknowledgement, and the paired agent, if any, has ended); a background launch's pending entry stays until SubagentStart pairs it and `helper_end` clears it, whichever of PostToolUse and SubagentStart lands first. "A real reviewer verdict was captured" is an explicit
pass condition of the record day (§6.7).

**How the command is read.** A linear, quote-aware pass (no backtracking regex on the command text; the pass stops at
200,000 characters and a longer command is refused as `oversized command`, fail closed): the text is split into
segments on unquoted `;` `&` `|` `(` `)` backticks and newlines, quotes removed, `#` comments and backslash-newline
continuations honoured (a backslash before `\n` or `\r\n` skips the whole line break), a backslash before a space kept inside the token (`/my\ dir/git`). The scan collects EVERY
publish in the whole command (not the first). Per segment:
* environment assignments and prefixes are skipped with the options that take a value, so the value is not read as the
  command: `sudo -u/-g ...`, `doas`, `env -u/-C ...` (`env -S "<string>"` is re-read as a command string), `nice -n`,
  `ionice`, `timeout [-s sig] [-k dur] DURATION`, `stdbuf`, `time`, `exec -a`, `nohup`, `command`, `setsid`, and the shell
  keywords `then do else if while ...`;
* the program name loses its path and `.exe`/`.cmd`/`.bat`/`.ps1` (`/usr/bin/git`, `git.exe`); a token holding a backslash
  outside quotes is also read with the backslashes removed (`g\it`), and backticks are also removed for a second whole-text
  pass (PowerShell's escape: `` gi`t ``); the hits of the two readings are merged by family (see the second reading below);
* wrappers are opened and the inner text read the same way, up to 4 levels deep (deeper = refused as `nested wrappers`):
  `bash|sh|zsh|dash|ksh -c` (also `-lc`, `-c -- '...'`), `cmd /c`, `powershell|pwsh` with `-Command`, `-EncodedCommand`
  (decoded), a `{ block }` or a bare string, `iex`/`Invoke-Expression`, `Invoke-Command`/`icm`,
  `Start-Process`/`saps`/`start` (FilePath plus ArgumentList split on commas), `eval`, `wsl [-e]`, `xargs` (options with
  a value skipped), `python -m <tool>`; package runners `npx|pnpx|bunx|uvx`, `npm|pnpm|yarn|bun dlx|exec|x`, `uv run`,
  `uv tool run`, `pipx run`, `poetry run` (their options with a value skipped, `@version` dropped from the package with an
  `@scope/` kept, `netlify-cli` read as `netlify`, `firebase-tools` as `firebase`, `npx -c "<shell command>"` re-read);
  `pnpm|yarn|bun <word>` that is not a package-manager subcommand is re-read as the command it runs
  (`pnpm wrangler deploy`);
* a double-quoted string that holds `$(...)` or a backtick, a here-string (`bash <<< "git push"`), and a heredoc body that
  a shell in the same command reads (`cat <<EOF | bash`) are scanned too. A heredoc body nobody executes (a commit
  message, `cat <<EOF > file`) is data and passes, except that (round 6) the body of an UNQUOTED delimiter that holds `$(` or a
  backtick is scanned too, because the shell expands it (`cat <<EOF` / `$(git push origin main)` / `EOF`). A `<<` after an unclosed `((`, `$((` or `$[` on its line
  (`echo $((1<<2))`) is an arithmetic shift, not a heredoc; a delimiter written `\EOF` is quoted like `'EOF'` and ends at `EOF`. Blocks, decided in the same pass where quoting is known: an UNQUOTED `{`
  that starts a token and an UNQUOTED `}` that ends a token (followed by a space, a line break, the end or one of `;&|()`)
  are segment boundaries like `;` and are dropped, so the contents of PowerShell and shell blocks are read as commands
  (`try { git push } catch { }`, `% { git push }`, `Measure-Command { ... }`, `function p { git push }`, `. { ... }`).
  A brace inside a token (`HEAD@{1}`, `${x}`, `@{u}`, `file.{a,b}`, `@{`) and every quoted brace (`-c "k={v}"`, `'{x}'`)
  stay plain text, and a closing `}` that balances a `{` of its own token is not a boundary. An unquoted `{#` stays text
  (so the `#` is not read as a comment), and an unquoted `{}` at a word start (`find . -exec rm {} ';'`, `{}/..`,
  `{}.d`) is kept as text, whatever follows it.
  **Second reading.** Whenever the text holds a brace it is read a second time in the PowerShell-braces mode, where EVERY
  unquoted `{` and `}` is a segment boundary, except the `${name}` variable syntax; quoting stays known, so a quoted brace is
  never a boundary in either reading. This catches blocks written without spaces (`%{git push}`, `try{git push}catch{}`,
  `.{git push}`, `if($x){a}else{git push}`, `do{git push}while($false)`, `$sb={git push}`, `-ScriptBlock{git push}`,
  `icm{git push}`, `function p{git push}`, `&{git push}x`). The reading is chosen ONCE per whole command, at the top: each
  reading (plain, PowerShell-braces; and each again without backticks) scans the whole tree of wrappers with that one
  reading, never forking at a nested level (a fork per level would cost 2 to the power of the depth and outlast the
  hook's timeout). The hits of the readings are merged by family: each family counts as often as the reading that saw it
  most, so every distinct publish takes an allowance. **Work budget:** the characters scanned over every wrapper level
  and every reading are summed; past 4 x 200,000 the scan stops and the command is refused as `unreadable command`
  (fail closed), so a command built to be slow is denied instead of timing out (a timed-out hook lets the command run).
  Harmless false positives of the second reading, kept: an unquoted brace before a dry-run flag
  (`git push {a,b} --dry-run`, `git push origin HEAD@{1} --dry-run`) is read as a plain `git push`.
  In the second reading a `#` right after a brace is never a comment (so `echo {#}; ...` cannot hide what follows);
  kept false positive: `&{x}#c; git push` is read with `#c` as text. Further odd-form limits are accepted: the gate
  targets ordinary and accidental publishes, not a determined adversary.
  **`find`.** `find ... -exec|-execdir|-ok|-okdir <command> ... ;|+` reads the tokens after each such flag, up to the
  terminator, as a command, like `xargs`. The terminators are the token `;` (quoted `';'`), `+`, and the lone `\` that is
  left of an unquoted `\;` (the unquoted `;` itself cuts the segment, as in the shell it would run; it is NOT turned into text,
  because in PowerShell `echo \; git push` really runs `git push`). The rest of a find after such a cut is a segment whose
  first word starts with `-`, `!` or `,` and that holds an exec flag; it is read as a find, so several `-exec` in one find
  are all read, also behind other primaries (`find . -exec true \; -print -exec git push \;`, `... ! -name x -exec ...`,
  `... , -exec ...`, `... -o -exec ...` are publishes; `find . -exec echo {} \; -exec echo git push \;` is not). Limits:
  a find run from a script or alias is not read; `-exec sh -c '...'` is read through `sh -c`; and any segment that starts
  with `-`, `!` or `,` and holds an exec flag is read as a find (`-print -exec git push \` after a `;`: false positive, kept).
  A PowerShell assignment prefix
  (`$x = ...`, `$null = ...`, `$x=...`) is skipped. **Known false positive (kept):** a double-quoted string that holds
  `$(...)` or a backtick is read as a command, so `echo "$(date) git push"` is treated as a publish.

A matcher that raises, or any failure to read the command, denies (`unreadable command`). **Exempt:** a segment that
starts with the documented `tools/anchor_ledger.py` (the bypass guard's own path rules: the Atlas checkout or one of its
worktrees, relative path only from such a cwd, no redirection or substitution): its push belongs to the approved anchor
design. A second command in another segment is judged on its own.
**Honest limits (the gate stops honest mistakes and the plain forms, not a determined bypass):** git aliases; scripts that
publish internally (`make deploy`, `npm run release`, `./deploy.sh`); `python -c` and other interpreters; `echo "git push"
| sh`; commands built at run time; **non-shell tools** (MCP servers, browser automation, an editor's own git); other
upload tools (`rsync`, `scp`, `curl -T`, `surge`, `railway` ...); and a **forged grant**: a script that writes the state
cache (`state/<sid>.json`) or the ledger directly is stopped only by rule B, the hash chain and the outside anchor, not by
this gate.

**The grant.** `/allow-publish` grants ONE publish, `/allow-publish N` grants N (1 to 5; more is clamped to 5). One
allowance = one publish: a command holding three publishes (`git push && gh pr merge 3 && npm publish`) needs three
allowances and is denied outright, without using any up, when fewer are left; when allowed, all are used up together and
each logs its own `publish_allowed {what}`. It is a user-only skill, a mirror of `/grant-rework` (§6.4):
`hooks/skills/allow-publish/SKILL.md` with `disable-model-invocation: true`, installed by `tools/install_hooks.py`; the
model invoking it through the Skill tool is denied in every mode (logged `ignored`); it is refused inside `CronCreate`,
`ScheduleWakeup` and `SendMessage` like the other two (`USER_ONLY_RE`); and it is honoured ONLY from UserPromptSubmit whose
prompt STARTS with `/allow-publish`, never from a helper, and only on an interactive entry (the `interactive_entries`
rule of §6.4a, same fixed fallback `cli`, `claude-desktop`, `claude-vscode`; otherwise `ignored` "publish grant from
non-interactive entry"). It needs no open task. The hook logs `publish_grant {n, expires, entry}`; state keeps `pub_n`
(allowances left, capped at 5 when grants add up) and `pub_exp`. A grant **expires 30 minutes after it was typed or when
the session ends** (`session_end` zeroes it), and it is per session. **Only the MAIN session can use it**: a helper's
publish command is always denied, with or without a grant, and does not use one up.

**The deny never waits for the ledger.** A hook that runs past its timeout lets the command through, so the DENY is decided
before the ledger lock is taken, from a lock-free read of the state cache (`pub_n`, `pub_exp`): no grant, a helper, a
missing or unreadable cache (a cold cache is never rebuilt here) all deny at once. Since 2026-10-13 the cache is also not
trusted to ALLOW: an open grant in the cache is confirmed by the ledger's own `publish_grant` / `publish_allowed` events
for this session (read from the end of today's and yesterday's day files, without the lock; see §6.4c), and a mismatch
denies and logs `ignored` ("grant not in ledger"). The lock is taken only to use up a
grant, with a short wait (about 0.5 s); a busy lock denies and leaves the grant untouched. The refusal is logged
afterwards, best effort (about 0.2 s of waiting for the lock, then an unlocked line flagged `nolock`; a missing cache is
not recreated; the refusal never saves state). Measured on the build machine, a denied `git push` takes about 0.4 s end to end (Python start-up included)
with the lock held and a cold cache, and about 1 s when a grant exists but the lock stays held.

**Tamper resistance (honest limit):** the ledger, the state cache and `atlas_config.json` are plain
files a model could still write through a shell command. Mitigations: Edit/Write/NotebookEdit to
`<data>\ledger\` and `~/.claude/hooks/atlas/` are denied in every mode; each hook run
compares the config's mode with the last `mode` event and logs `tamper` on a mismatch; the Ledger
shows the tamper count. So the locks stop honest mistakes and make tampering visible; they do not
make it impossible. (Raised to the operator with the screen review.)

### 6.4c The config gate and `/allow-config` (2026-10-13)
The operator's rule: the files that define how Claude sessions and agents behave change only with the operator's OK. **In EVERY mode**
(record and enforce alike, like the publish gate), an Edit, Write or NotebookEdit on a config path, and a Bash or

against the session's working folder (`echo x > ../../../agents/evil.md` from `~/.claude/projects/<p>/memory`;
`echo x > ../atlas-data/ledger/x` from `<repo>`). A token that starts with an option prefix (`^(?:--?[\w-]*=|-[\w-]+:|[A-Za-z]\w*=)`: `of=`,
`--output=`, `-Path:`; no separator inside it, so `~/.claude/projects/a=b/../..` and `<repo>/x=y/../..` are not split) has
the prefix split off once (never recursively), the rest collapsed or resolved, and the prefix glued back; the token read
unsplit is ALSO kept as a variant (`dd of=../atlas-data/ledger/state/s.json`, `Out-File -FilePath:../atlas-data/ledger/x`,
`cp x --target-directory=../../../agents` from a memory folder). The hint pre-filter sees all readings.

**Globs and escapes (round 3).** A path token that names `.claude` (or `CLAUDE~<n>`) and holds a glob character (`?`, `*`, `[`),
or, in a POSIX-looking path (a `/` in the token), a backslash before a name character (`~/.claude/CLAUDE\.md`), cannot be
read literally, so a segment holding one is gated (label `glob-path`) unless it is a read: `echo x > ~/.claude/CLAUDE.m?`,
`cp evil.sh ~/.claude/sk?lls/x/run.sh`, `cp evil.py ~/.claude/hook[s]/x.py` are gated; `ls ~/.claude/skills/*` and
`cat ~/.claude/CLAUDE.m*` stay free. A glob or escape that only comes AFTER the `projects/` or `worktrees/` component is
free too (`rm ~/.claude/projects/*`, `rm -rf ~/.claude/projects/*/memory/tmp`, `echo x > ~/.claude/projects/*/memory/note.md`,
the same under `worktrees/`), unless the token holds `..` (`~/.claude/projects/*/../../agents/x` stays gated) or the text after
that component holds `claude`, `.mcp` or `mcp~` (`<repo>/.claude/worktrees/w/.claude/settings.jso?`, `.../w/CLAUDE.m?`,
`.../w/CLAUDE\.md`, `~/.claude/worktrees/w/.claude/agent[s]/x.md` stay gated). **Round 6 (2026-10-13):** below the first component
after `projects/` or `worktrees/` (the project or worktree name, which may itself be a glob: `worktrees/*`, `worktrees/agent-*`),
every glob component is matched (`fnmatch`, case-insensitive) against the config names (`.claude`, `claude~<n>`, `mcp~<n>`,
`CLAUDE.md`, `CLAUDE.local.md`, `SKILL.md`, `.mcp.json`, `.claude.json`, `settings*.json`, and the short names), and against the
folder names `skills`, `agents`, `commands`, `hooks`, `rules`, `output-styles`, `plugins` when they follow a `.claude`-like component;
a match gates (`w/.cl?ude/settings.json`, `w/.cl*/settings.json`, `w/CL?UDE.md`, `w/[C]LAUDE.md`, `w/.mc?.json`). A component that
holds a backslash escape counts as a candidate after the backslashes are removed (`w/.c\laude/settings.json`). A component that names
only an extension (`*.md`, `*.json`, `?.txt`) is not a match, so `echo x > ~/.claude/projects/*/memory/*.md` stays free; a bare `*` below
the project or worktree name is a match (`rm -rf ~/.claude/worktrees/w/*` is gated). The 8.3 short names `CLAUDE~1.MD` (`CLAUDE.local.md`) and `MCP~1.JSO` (`.mcp.json`)
are config names. Rule B also accepts the short names of the ledger folder and of the anchor clone
(`D:\AI\ATLAS-~1\ledger`, `D:\AI\ATLAS-~1`).

**The grant.** `/allow-config` opens a 15-minute window (no count: one change often needs several edits). A user-only
skill, a mirror of `/allow-publish` (§6.4b): `hooks/skills/allow-config/SKILL.md` with `disable-model-invocation: true`,
installed by `tools/install_hooks.py`; the model invoking it through the Skill tool is denied in every mode (logged
`ignored`); it is refused inside `CronCreate`, `ScheduleWakeup`, `SendMessage`, `RemoteTrigger`, the scheduled-tasks tools and the ccd_session tools
(`USER_ONLY_RE`, §6.4a), and as the first prompt of a spawned `claude` (§6.4); it is honoured
ONLY from UserPromptSubmit whose prompt STARTS with `/allow-config` (`^\s*/allow-config(?![\w-])`), never from a helper,
and only on an interactive entry (§6.4a; otherwise `ignored` "config grant from non-interactive entry"). It needs no open
task. The hook logs `config_grant {expires, entry}`; state keeps `cfg_exp`. The grant expires 15 minutes after it was typed
or when the session ends (`session_end` clears it), and is per session. **Only the MAIN session can use it**: a helper's
config change is always denied. It opens no other gate (publish, forged-grant and `: team-*` handling still run).

**The deny never waits for the ledger.** Like the publish gate: the deny is decided from a lock-free read of the state
cache (`cfg_exp`); no grant, a helper, or a missing or unreadable cache all deny at once (a cold cache is never rebuilt
here). **The cache is not trusted to ALLOW (round 3):** the state cache is a plain file and can be forged, so when the cache
shows an open grant, the gate also confirms it in the ledger (`ledger_grant_state`): this session's `config_grant` event
(without an `agent_id`) is read from the end of today's day file, and of yesterday's for a grant just after midnight, back to
two hours ago or this session's last `session_end`, bounded to 16 MB per file, without the lock and without rebuilding any
state; a grant that is not live in the ledger denies and logs `ignored` ("grant not in ledger"). **Expiry cap:** a replayed
grant never outlives its own timestamp plus its window (`t` + 15 minutes for `config_grant`, `t` + 30 minutes for
`publish_grant`), whatever `expires` the event carries (a forged line with a one-day expiry and a `t` 20 minutes ago denies);
a grant line whose `t` cannot be parsed, has no timezone or is more than 2 minutes in the future is skipped, and never fails the whole scan. The publish gate (§6.4b)
does the same for `publish_grant` / `publish_allowed` (it replays the allowances, so a forged `pub_n` above the ledger's
count denies). The lock is taken, with a short wait (about 0.5 s), only to log an allowed change as `config_allowed`; a busy lock
denies. A refusal is logged afterwards, best effort (about 0.2 s of waiting, then an unlocked line flagged `nolock`; it never
saves state). Every allowed change and every refusal is recorded: `config_allowed {path | what, tool}` and
`refusal {guard: "config", would: false, path | what, tool, actor, detail}` (§1.2). A config refusal is not a rework
refusal: the Ledger's rework counts and the bypass reading look at `guard: "rework"` only.

**Honest limits (the gate stops honest mistakes and the plain forms, not a determined bypass):** a script that writes a
config file internally (`py fix.py`, `make`, a build step, `python -m <module>`), a patch applied from a file or stdin
(`git apply`, `patch`: the target path is inside the patch, not on the command line), a path built at run time, a config
file copied or synced from a folder whose files are not named on the command line (`rsync -a /tmp/cfg/ D:/repo/`),
aliases, run-time argument values (`$a='/allow-config'; Start-Process claude $a`, a path or command read from a variable
or a file), a glob or escape inside the folder name itself (`~/.cl?ude/...`, `~/.cl\aude/...`; only tokens that spell
`.claude` literally are caught), a wipe by absolute path with a bare `*` below a project or worktree name
(`rm ~/.claude/projects/<p>/memory/*`, `rm -rf .../worktrees/w/*`) is gated although nothing there is config (a known false
positive: use a cwd-relative `rm *`, a named file, or ask the operator), a `..` inside a path that holds a space (the token split cuts it), and **non-shell tools** (MCP
servers other than the forwarding tools listed above, an editor's own save, a browser). Closed in round 3: an open grant no
longer switches off the publish and forged-grant checks, `..` is collapsed in both guards, the grant is confirmed in the
ledger, the spawned-claude check reads quote- and backtick-stripped text, globs and escapes, and the 8.3 short names of
`CLAUDE.local.md`, `.mcp.json` and the ledger and anchor folders. Closed in round 2 (2026-10-13): the bare folder
`~/.claude` (`claude-root`), a relative write after `cd` into a config folder, a config file copied into a folder, a path in
one segment run by a later one, short names, quotes inside a path, the `git` upgrade abuse, an interactive `claude`
handed a user-only command. The ledger, the
hash chain and the outside anchor remain the other layers, and the Ledger shows the allowed changes.

### 6.5 The done-lock
A consult of the `advisor` helper is no check: it never marks changes as checked and never satisfies the lock.
* **Version:** each task has `version`, +1 on every non-exempt `edit`. Exempt paths: anything under
  `~\.claude\` (memory, plans; its config files are not exempt, see the end of this bullet), the session's scratchpad / the system
  temp dir, `<data>\`, and files whose name ends in `build-log.md` or `.notes.md`, and scratch files: a name that starts with `scratch-` and ends in `.md`, a name that ends in
  `.scratch.md`, or a `.md` / `.txt` file inside a folder named exactly `_scratch`. The path is normalised first;
  names match case-insensitively, on whole path components. Never scratch: any path with a component starting
  with `.` (`.claude`, `.github`), and the names `claude.md`, `claude.local.md`, `agent.md`, `agents.md`, `skill.md`,
  `gemini.md`, `cmakelists.txt`, `requirements.txt`. *(2026-10-19)* A config path (§6.4c) the gate allowed IS recorded as an `edit`
  (it bumps the version and needs a check before done), even under an exempt folder above (a config path is never exempt).
* **Path forms (2026-10-13).** Every path check looks at TWO forms of the path: the absolute one (`norm_path`) and the
  real one (`realpath`, so junctions and symlinks are resolved; if it cannot be resolved the absolute form stands in),
  and the same two forms of each root (ledger dir, hooks dirs, anchor clone, exempt dirs). Fail-safe: a path is
  **protected** (ledger, hooks folders, anchor clone) when ANY form is under ANY form of a protected root, and is
  **config** (§6.4c) when ANY form matches; it is **exempt** only when EVERY form is exempt on its own (so a junction
  named `_scratch` that points at a source folder exempts nothing). NTFS alternate data streams: a path whose part after
  the drive holds a `:` (`x.md:s`, `file::$DATA`) is NEVER exempt or scratch; for the protected and config checks the
  stream suffix is stripped first (everything from the first `:` in the last component, and trailing dots and spaces), so
  `CLAUDE.md:x` is config and `ledger\file:x` is protected. `norm_path` itself is unchanged.
* **Closing:** PreToolUse `: team-done`: allowed when the task's type has `needs_check: false` and
  no edits, or `version == 0`, or a READY verdict (or ok check) exists at `version == current`.
  Otherwise refuse: `"Not closed: version <v> has no passing review (last READY at version <m>). Run
  the reviewer on the final version, then close."` Also refused (guard `done_lock`, since 2026-10-26), whatever the
  version or budget (so a task worked only through the shell cannot slip out): a task with an open failing review,
  `(nc_count > 0 and not task_resolved) or escalated`: `"Not closed: the last review of this task did not pass. Run a fresh
  reviewer on the fixed work, or declare the next piece of work (this task is then recorded as abandoned with open
  findings)."` Either check failing refuses (record mode logs `would: true` and still closes). A READY from a reviewer
  launched after the latest NEEDS CHANGES resolves it and the task closes normally; an escalated one stays refused until a
  grant clears `escalated` or it is resolved.
* **Stop send-back:** on Stop, if the current task is open, `needs_check` (or it has edits), `version
  > last_verified`, `stop_hook_active` is false, `sent_back_for != version`, **and no pending builder younger than 2 h
  is still running** (a builder `helper_start` with no `helper_end`): block once with
  `{"decision": "block", "reason": "Unchecked changes (version <v>, last check at <m>). Run the
  check now, or tell the operator plainly that the work is not checked yet."}` and set `sent_back_for =
  version`. Never more than once per version.

### 6.6a The declare guard (2026-10-15)
PreToolUse `Agent`, in the **main session only** (never inside a helper's scope, `agent_id` empty), when the session
has no open declared task → refuse with:

> Declare the work before launching a helper: run `: team-type <type> [area]` on its own (coding, research, writing,
> legal, chore, quick-question; add the area when the folder is not the topic's), then launch the helper again.

Declared = an open task whose type is not `undeclared`: opened by `: team-type`
(`work_type`, any type, `quick-question` included) or by a playbook (`playbook`). Not declared = no task yet, the last
task closed by `: team-done`, or the open task is the implicit `undeclared` one opened by an edit. Logged as
`refusal {guard: "declare", would, helper, label, tuid, detail}` (§1.2; `would: true` in record mode, where the spawn
is allowed; no prompt text, no tool input). Its `task` is the session's last task, which may already be closed; reports
never let a `declare` refusal change a task's result. It is a nudge, not a barrier: any declaration lets the spawn through. It runs before the §6.6 and §6.3 checks. Edits without a declaration still open the
implicit `undeclared` task; nothing else changes. The daily check counts `declare` among the normal-flow refusals.

### 6.7 Modes: record-only first
`atlas_config.json` → `"mode": "record"` or `"enforce"`. In **record** mode every guard computes its
decision, logs it (`refusal` / `sendback` with `would: true`) and **allows** (no deny, no block).
In **enforce** mode it denies/blocks and logs `would: false`. Exception in both modes: the model
invoking `grant-rework`, `ack-break`, `allow-publish` or `allow-config` is always denied, and so are a publish command without a grant (§6.4b) and a config change without a grant (§6.4c). Switch: `py -3.12 tools/hooks_mode.py record|enforce`
(edits the installed config, appends a `mode` event). Start = record. Enforce only after one full
day of records shows no wrong refusal **and** at least one real reviewer verdict captured with the
right version, and the interactive `CLAUDE_CODE_ENTRYPOINT` values recorded (the orchestrator checks, logs the
evidence in the build log).

### 6.8 Areas/look check
On PostToolUse Edit/Write of a file named `areas.yaml` or `look.css` inside a git repo that has
`tools/check_look.py`: run it (`<python.exe> <repo>/tools/check_look.py --json <file>`, 3 s timeout),
log a `check` event; if it fails, return `additionalContext` with the problems (both modes; it
informs, never blocks). An edit to `areas.yaml` or `workflows.yaml` also refreshes the hooks' JSON

### 6.9 Edit reminder (3-edit rule)
On PostToolUse Edit/Write, for a non-exempt edit by the MAIN session (no `agent_id`) on a task where the reminder
applies, the hook counts main-session edits per task (reset
when a task opens; helper edits do not count). On the 3rd, 6th, 9th, ... it returns `additionalContext`: "3-edit rule:
this is the main session's 3rd edit on this task. Brief implementer (code) or drafter (text) with the rest, unless the
change is tiny or a hard case." (`6th`, `9th`, ...). It joins a check failure message when both apply. It informs,
never blocks, in both modes; no ledger event is written and no text is stored. Any error in it is swallowed.
The reminder applies when: the type's crew (`workflows.yaml`) includes a builder; the type is `undeclared` (its real
type is unknown); the type is a playbook whose `playbook_crews` entry includes a builder, or that playbook is not
listed there. It is also assumed to apply when the type is not listed in `workflows.yaml`, `workflows.yaml` is
unreadable, or a crew is not a list (malformed). A Claude memory file (any path under `~/.claude/projects/<project>/memory/`)
is never a counted edit: it is exempt from this reminder's count and from the stop below.

**The 6-edit stop (since 2026-11-03).** The reminder above is unchanged. State adds `builder_edits`: the main-session
edits on the task since the last `implementer` or `drafter` launch (counted exactly like `main_edits`, so the same
exemptions and the memory exemption apply). It is 0 when the task opens and is reset to 0 by every `helper_start` of
`implementer` or `drafter` on that task. On PreToolUse Edit/Write/NotebookEdit by the MAIN session (no `agent_id`), when the
task is open, `builder_edits >= 6` and the type's crew can reset it: the crew (or the playbook's `playbook_crews` entry) includes
`implementer` or `drafter`, the helpers whose launch resets the counter (a `researcher` or `sweeper` is a builder for the reminder but
cannot reset the stop, so a research-only crew is never stopped; an `undeclared` task is stopped (its type is unknown); the reminder is unchanged), the hook calls `refuse()` with guard `edit_limit`: record mode logs `refusal {guard: "edit_limit", would: true}`
and allows, enforce mode denies. Reason (one line): "Main-session edit limit reached on this task (6 since the last
builder): hand the rest to implementer or drafter." Helpers' edits are never refused by it. Any error in the check is
swallowed (fails open). It is checked after the quick-question and rework guards. Opening a new task (re-declaring with `: team-type`) resets the counter by design, because the abandoned task shows on the Ledger.

### 6.9a Test-runner reminder before a review (since 2026-11-03)
On PreToolUse Agent in the main session launching a reviewer (`reviewer` or `senior-reviewer`) for a task of type `coding`:
if an `implementer` has returned on this task (`helper_end`) and no `test-runner` was launched after that return, the hook
adds one line to `hookSpecificOutput.additionalContext` of that PreToolUse answer (the same channel as §6.3a; it never
changes the permission decision, so it is never a deny): "Reminder: an implementer returned on this task and no
test-runner has run since. Run the full suite with test-runner before the review." State: `ord_n` (a monotonic counter
bumped by every `helper_start` and `helper_end`, so the order never depends on list order), `impl_ret` (`ord_n` at the last
`implementer` `helper_end` of the task, null before) and `tr_launch` (`ord_n` at the last `test-runner` `helper_start` of the
task, 0 before); both reset when a task opens. The reminder fires when `impl_ret` is set and `tr_launch <= impl_ret`. No
ledger event is written; any error is swallowed (fails open).
