# Atlas v2: build contracts

> The shapes every lane builds against. Written in Wave 0 (2026-10-09) from the approved scope
> and the research notes.
> A lane that needs a shape not written here stops and asks the orchestrator; it does not invent one.
> Changing a contract after Wave 1 starts = an orchestrator decision recorded in the build log.

Conventions: Python 3.12 (`py -3.12`), stdlib + `pyyaml` only (no new dependency without the orchestrator).
Paths below are relative to the repo root unless absolute. Python module names are as imported by
the server, which puts `cockpit/` and `dashboard/` on `sys.path` (so `import ledger2.query`,
`import plan.api`, `import teamlive`, `import usage`). Times are local ISO-8601 with seconds and
offset (`2026-10-09T14:20:05+02:00`). Every JSON API answers `{"ok": true, ...}` or
`{"ok": false, "error": "<one line>"}` with the HTTP code given per endpoint.

## 1. The ledger: events

**Where:** `<data>\ledger\` (outside the repo; override `ATLAS_LEDGER2_DIR` for tests, which
MUST use a temp dir). Layout:

```
ledger/
  events-YYYY-MM-DD.jsonl   append-only, one JSON object per line, never rewritten, never pruned
  v1/events.jsonl           the imported v1 dispatch history (§1.6), regenerated by the importer only
  state/<session_id>.json   the hooks' per-session cache (§1.4), rebuildable from events, may be deleted
  state/offsets-<sid>.json  per-session transcript offsets + recent message ids for cost capture (§1.5)
  auto/<marker>.json        automatic-session markers written by the launcher (§7)
  .lock                     the append lock file
```

**Writing:** one line per event, UTF-8, `ensure_ascii=False`, < 4 KB (truncate any string field to
200 chars before writing). Lock = open `.lock`, `seek(0)`, `msvcrt.locking(fd, LK_NBLCK, 1)` in our own
loop, 20 tries × 50 ms; if not obtained, proceed without it: never lose an event, never block a
session. The cost pass (§1.5) reads transcripts OUTSIDE the lock; only its appends and its
offsets/state write take it. The hook holds that lock across **read state → append event(s) → write state**
(`state/<sid>.json.tmp` then `os.replace`), so concurrent hook processes (parallel tool calls) never
lose a version bump or a pending entry. Each append = the file opened in append mode and ONE
`write()` of the whole line.
**Hash chain (amendment, screen review 2026-10-09; see §6.4 rule A):** every line carries `prev` =
the sha256 (hex) of the PREVIOUS line's bytes in the same day file, without its line ending; the first
line of a day carries the sha256 of the last line of the nearest earlier day file, or `"genesis"` when
none exists. The append computes it under the lock (`store.append_events`, and the hook's own
`append_lines`). `store.verify_chain()` walks the day files in order and returns `{intact, breaks:
[{file, line}], files, lines}`; lines written before the chain existed (no `prev`) are accepted until
the first chained line. A deleted or edited line shows as a break at the line AFTER it; `verify_chain` accepts a `prev` equal to the hash of
any of the previous 8 lines ONLY for a line flagged `nolock` (appends that raced without the lock chained to a slightly
stale tail), for the first line of a day file (backfill shape) and for the first chained line after legacy lines; every
other line must link to the line right before it, so lines inserted without `nolock` produce a break. The lock is retried for
~3 s before an append proceeds without it, and such lines carry `"nolock": true`; every append is one `write()` on an
O_APPEND handle, and a line still being written by another process is not used as the tail. Limits: the
last line of the newest file can be cut or edited without a trace, and an event appended to a day file
that already has a later neighbour (backfill) reports a break; the chain makes tampering visible, it
does not prevent it.
**Break triage and acknowledgement (decision 2026-10-10).** The walk lives in the stdlib-only
`cockpit/ledger2/ledger_chain.py` (the installer copies it next to the hook, like `areas.py`). A break has a stable id
`<day>:<line>:<hash8 of the broken line>:<hash8 of the previous non-blank line in scan order>` (for example
`2026-10-09:120:ab12cd34:9f00e1a2`); binding the predecessor means that editing the line before an acknowledged break
makes it a new, unacknowledged one. For every break the code computes, deterministically and without a model, signs of
an accident (6 shown: within the last 8 lines of the day file; flagged `nolock`; cut off or unreadable; time within 1 s
of a neighbour; `prev` points to another existing line; the previous day file ends earlier than this line expects) and
signs of tampering (in the middle of the history and not flagged; `prev` matches no line; a `refusal`, a NEEDS CHANGES
`verdict` or a `bypass_attempt` right next to the break), then a verdict "Looks accidental: N of 6 signs: ..." /
"Looks like tampering: ..." / "Unclear: ...". `nolock`, end-of-file position and same-second time are signs only, never
sufficient. Rules: (i) `prev` matching NO line is never accidental: tampering, or unclear when the line is flagged
`nolock` or the previous day file ends earlier than expected; (ii) a cut-off line is accidental only if the next
non-blank line (same or next file) has `prev` equal to the hash of the cut-off line or of the line before it, or the
cut-off line is the last line of the ledger, else unclear; (iii) a `prev` pointing to another existing line is
accidental only if that line or one of the 8 before it carries `nolock`, or it is the backfill shape (first line of a
day file pointing into the previous day file), else unclear. An acknowledgement (`integrity_ack`) counts only if its own
line is not a break, it has no `agent_id`, `by` is `operator`, and the latest prompt event of the same `sid` has
`cmd` = `ack-break`. Status: "intact" (no break), "intact, N acknowledged" (every break acknowledged) or "broken"
(any unacknowledged break); a NEW break is unacknowledged, so it turns the status red again.
**Plain limits of the chain.** There is no secret key: whoever can write the files can re-chain every line from an edit
point to the end, and that leaves NO break. The chain finds crude edits, insertions, deletions and reorderings, nothing
more; the window tolerance exists only for `nolock` lines. An edit to the newest lines of the newest file cannot be
detected until the next write chains onto it.
**Outside anchor.** Detects edits to closed days of the ledger, including a full re-chain, as long as the GitHub ruleset
stays in place. Pushes use the operator's existing account SSH key (no passphrase prompt); removing the ruleset needs a browser
session logged in to GitHub, which is the one thing to keep away from agents. The ruleset also requires linear history. How it works: `tools/anchor_ledger.py` runs daily (Windows task `AtlasLedgerAnchor`, 21:00) and
appends `{day, lines, last_hash, anchored_at}` (plus `head: true` while the day is still open) for the last
newline-terminated, non-blank line of each day file to `anchors.jsonl` in a separate public git repo (hashes only), commits, and runs
`git push <pinned url> HEAD:main`. The pinned remote lives in the versioned file `anchor.json` at the Atlas root
(`url` = `git@github.com:example/atlas-anchor.git`, `branch`, `clone` = `D:\AI\atlas-anchor`; the clone path can be
overridden with `ATLAS_ANCHOR_REPO`; the file named by `ATLAS_ANCHOR_CONFIG` replaces it, for tests). The GitHub branch
ruleset blocks force pushes and deletions. The tool never prompts (`GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, SSH
`BatchMode=yes`), never rewrites or "corrects" an entry, and exits non-zero on a mismatch (2), a commit or push failure
(3) or a setup error (1: no git, no clone, no config).
**The local file is not trusted.** The integrity check runs `git fetch <pinned url> main` in the clone from a background
thread (cached, TTL 10 minutes, never inside a request) and builds the anchor set from the whole remote history of
`anchors.jsonl`: every version must be a byte-prefix of the next one, any other change is broken, "Looks like tampering:
the outside anchor file was rewritten." The local file must equal the remote file plus not-yet-pushed appends, else
broken, "the local anchor file differs from the outside copy". Each entry says "the Nth non-blank line of that day file has
this hash"; a changed or missing line is broken, never acknowledgeable, never "accidental": "Looks like tampering: the
record of <day> no longer matches its outside anchor of <date>". An entry that is not a valid object (day `YYYY-MM-DD`,
`lines` a positive integer, `last_hash` 64 hex, `anchored_at` ISO) or a final line without its newline is reported as
"an anchor entry is unreadable", never dropped. Remote unreachable is amber (`remote: "unreachable"`, `unreachable_since`),
never a silent fallback to the local file. The payload `anchor` holds `{configured, expected, missing, last_anchored_day,
last_remote_commit_at, last_push_ok_at, remote, unreachable_since, mismatches[]}`; the panel shows amber when the newest
remote commit is older than 2 days and red when older than 7 days.
**Hardening of the check.** The fetch goes into a fresh temporary bare repo (never the clone), with no system or global git
config, `protocol.allow=never` except ssh, `core.autocrlf=false` and a forced `GIT_SSH_COMMAND=ssh -o BatchMode=yes`; the
push uses the same environment plus `remote.pushDefault=`. A `url.*` key in the clone's own config is tampering. Any
merge commit in the fetched history is tampering (history is read with `--full-history`, all versions in one
`git cat-file --batch`). The tool commits `.gitattributes` with `anchors.jsonl -text` and compares the local file with
`git show HEAD:anchors.jsonl`, so a CRLF checkout is not an edit. Unreachable remote: amber, red after more than 2 days once
`anchor_configured` exists, and never rendered as "all match". With `anchor_configured` present, `ATLAS_ANCHOR_DISABLE` or
`ATLAS_ANCHOR_CONFIG` in the cockpit environment shows amber "check disabled". The Edit and Write tools are denied on the
clone path, and the Bash guard lets only `tools/anchor_ledger.py` name it.
**Limits.** This raises the bar against accidental or clumsy tampering; it is not proof against an agent that can edit
Atlas's code, `~/.ssh/config` or `known_hosts`, or drive a browser logged in to GitHub.
**"Configured" only grows.** On the tool's first successful push it appends one `anchor_configured` event to the ledger
(`url`). Once that event exists, a missing config, clone or `anchors.jsonl`, or an empty anchor set, is broken: "Outside
anchor missing". With no event and no anchor file the panel says "Outside anchor: not set up" and the status is unaffected.
**Still open:** lines written after the last anchor run (today's open day) are covered only from the next run; whoever
holds the operator's GitHub login can remove the ruleset and then rewrite the remote; and anyone who can write the PC can stop the
daily task (the staleness warning is the only signal).
**Metadata only: never prompt text, never tool input text, never tool output text**, except the fields
explicitly listed below (task labels ≤ 60 chars, the orchestrator's summary, paths of edited files).
The denied command itself is NEVER stored, not even for `bypass_attempt` (decision 2026-10-10): the hook
classifies it in memory and keeps only derived labels (`effect`, `target`). The one free-text field a
`bypass_attempt` carries is `desc`, the agent's own stated intent (the Bash `description`), clipped to 160 chars
and masked BEFORE the clip, because an agent's words can hold secrets too: any `NAME=value`, `NAME: value` or
`set|export|-e NAME value` whose name contains `password`, `passwd`, `pwd`, `token`, `secret`, `api_key`,
`access_key` or ends in `_key`; `--password`/`--token` style flags; `-u user:pass`; URL credentials
(`scheme://user:pass@`); `Authorization:`/`Authorization=` and `Bearer` values; `mysql -pSECRET`;
`sshpass -p SECRET`; `sk-`/`pk-`/`glpat-`/`xox?-`/`ghp_`/`gho_`/`ghs_`/`ghu_`/`github_pat_`/`npm_`/`hf_`/`AKIA`/
`AIza` tokens; and hex or base64-like runs of 24+ characters (a run with `/` is kept only when every `/`-piece
looks like a path name). Only the first 4096 characters are processed.
**Trust rule for reports:** facts in a bypass report are computed by code from the ledger and can be trusted; a
note (`bypass_note`) is the main session's account of the events, to be read with care, and never overrides the
facts.

The `task` field is the **current task id** of the session at the time of the event (or `null` if no
task is open). A task id is `<first 8 chars of sid>-<n>`, `n` = 1, 2, ... in order of the task-opening
events (`work_type`, `playbook`, implicit `undeclared`) in that session. `derive` takes the id from
the opening event's `task` field and never recounts.

Task-opening rules:
* `: team-type <type>` with an optional second word = area id (`: team-type coding atlas`). The area
  word is optional; `team_events.py`'s regex is widened (one-line change, Lane 1) so the Team panel
  keeps its type label.
* `: team-type <type> [area] [task:<id>]` (since 2026-10-10): an optional LAST token `task:<id>` links the task to a
  Plan item. `<id>` is a calendar event id (`evt_` + 8 hex), a series occurrence (`evt_xxxxxxxx@YYYY-MM-DD`), a
  `tasks.yaml` id (`t_` + 8 hex) or a project plan.yaml id (`<project>/<task id>`). Order is area then task; the task
  token may be given without an area. The id is stored on the `work_type` event as `plan_ref` and in the hook state
  (`plan_ref`); the format is validated (the value is stored exactly as validated, case-sensitive in both hooks), the arguments are capped at 120 characters (longer = `ignored` bad arguments) and parsed by splitting words, never by a backtracking regex, and free text is never stored: a malformed id is logged as
  `ignored {what: "team-type: bad plan ref"}` and the type is still declared (no `plan_ref`). `team_events.py`
  (the Team panel's log) records the same validated `plan_ref` on its `WorkType` record, and logs no `WorkType` at all when the declaration fired inside a helper (the Team panel also drops any such record on read). The id is NOT checked
  against the Plan at declaration time (the hook never reads the Plan); it is resolved on read (§1.7, §5.1).
  `tools/find_plan_item.py "<name words>" [--day YYYY-MM-DD]` finds the id (§5.3).
* **Automatic Plan link** (since 2026-10-12): when the hook opens a `playbook` or `work_type` task WITHOUT an explicit `task:<id>`, it looks for the Plan item the session was run for. Never for the implicit `undeclared` task; an explicit `task:<id>` always wins and is unchanged. Candidates are today's calendar events (`GET <plan_url>/api/v2/plan?from=<today>&to=<today>`, section 5.3) with the SAME area as the task being opened, with a start and end time (all-day skipped), not `done`, and running now or starting within 15 minutes (`start - 15 min <= now < end`, local time). Exactly one candidate links; zero or several = no link (never a guess). The ref is the row's id: `evt_xxxxxxxx` for a single event, `evt_xxxxxxxx@YYYY-MM-DD` (the row's `occurrence`) when the row has `recur`; it is validated with the same pattern as an explicit ref. It is stored as `plan_ref` plus `plan_auto: true` on the opening event, at task open only (never revised later); `derive` copies both into the TaskRecord (`plan_auto`, false when absent). `plan_url` comes from `hooks/atlas_config.json` (key `plan_url`, default `http://127.0.0.1:8765`), overridden by the env var `ATLAS_PLAN_URL`; a present-but-empty, null or `off` value (either place) switches the feature off, the default URL applies only when the key is absent; only a loopback host (127.0.0.1, ::1, localhost) is used, with no proxy; a malformed `task:` token counts as explicit (no automatic link); helpers never trigger the read; an automatic ref is not an explicit one for the 60 s duplicate rule (an explicit `task:` after it re-opens the task); `install_hooks.py` keeps an installed `plan_url`. The read is stdlib `urllib` with a 0.5 s timeout per socket operation (redirects are not followed: a 30x means no link), done BEFORE the ledger transaction (never under the lock), only when a bare declaration or playbook is about to open; any failure (server down, bad JSON, timeout) = no link, silently, and the hook never reads `schedule.yaml`.
* An explicit declaration always opens a **new** task, even with the same type as the open one (the old
  task is closed as `switched`). The spent count carries on any re-declaration while the open task is at/over
  budget and NOT RESOLVED, or escalated, whatever the type; under budget every declaration starts fresh. **Resolved**
  (2026-10-10) = the task's most recent reviewer verdict is READY and that READY covers the latest main-session version
  (`last_verified >= version`) AND whose reviewer was LAUNCHED after the latest NEEDS CHANGES arrived (a reviewer started
  in parallel with the failing one cannot clear it: A and B launched together, A answers NEEDS CHANGES, B answers READY =
  still unresolved). A reviewer the main session RESUMES with SendMessage after the NEEDS CHANGES counts as launched at
  the resume: the hook emits `helper_resume {task, agent_id, helper}` when a SendMessage from the main session (not from
  a helper, and not a refused user-only command) has `to` equal to the `agent_id` of a helper already paired in this
  session whose previous run has ENDED (`ended_ids`; a still-running helper, a helper sender or an unknown `to` changes
  nothing). It bumps `spawn_seq` and gives that agent the new `seq`, and, like a fresh launch, the current `version` and
  `task`. The resumed helper's next SubagentStart keeps its pairing (it never claims a pending launch) and re-opens its
  verdict capture; a stale SubagentStop replayed before that is not a verdict. Only verdicts arriving after the resume
  use the new seq; earlier ones are never resurrected. `derive` mirrors it: a `helper_resume` counts as a new
  launch of that `agent_id`, and a resumed helper's later verdict is not dropped as a duplicate. The hook keeps `last_verdict`, `last_verdict_seq` (the launch order of the reviewer), `nc_at` (how
  many helpers had been launched when the latest NEEDS CHANGES arrived; kept across a carry) and `spawn_seq`; `pending`
  and `agents` entries carry `seq`. `derive` mirrors it from the order of `helper_start` events (a helper's launch id, or
  its `agent_id` through `helper_paired`). Honest limits: a READY on an unrelated artifact, or from a reviewer that was
  told to answer READY, still counts. Also: a foreground reviewer's SubagentStop and PostToolUse can race around a
  resume (the first to land is the verdict); a SubagentStop replayed after the resumed run's SubagentStart is taken for
  the new run's verdict; resuming a non-reviewer only bumps `spawn_seq`.
  The main session's `version` counts only edits made in the main session (helpers edit in their own worktrees), so a
  count of NEEDS CHANGES with `version` 0 is NOT proof of an unresolved task. A task opened by a carry has no verdict
  yet, so it is unresolved and the next declaration carries again (the double-declaration escape stays closed) until a
  READY lands on it.
  Only an exact duplicate within 60 s (accidental double call) is a no-op (logged as `ignored`), unless a `task:` token names a different Plan item than the open task's `plan_ref` (that opens a new task).
* Switching type while the open task has `needs_changes ≥ budget` or is `escalated` carries
  `needs_changes`, `escalated` and `granted` into the new task and logs `refusal{guard: rework}`;
  the new task's effective budget = min(old budget, new budget), stored in state (`derive` applies
  the same rule).
* A non-exempt edit with no open task opens an implicit task of type `undeclared`
  (`needs_check: true`, `default_budget`).
* Playbook names = those listed in some area's `playbooks` or in `workflows.yaml` `playbooks:`; only
  those open a `playbook` task; the same command within 10 s opens one task, not two.
* `: team-*` commands issued inside a helper (`agent_id` present) are ignored (`ignored` event).

### 1.4 Per-session state cache (`state/<sid>.json`), hooks only

```json
{"sid": "...", "task": "abcd1234-2", "n": 2, "type": "coding", "area": "atlas",
 "version": 7, "last_verified": 5, "needs_changes": 1, "escalated": false, "granted": 0,
```

A cache only: if missing or unreadable, the hook rebuilds it by scanning back day files to the one

### 1.5 Cost capture

At every `Stop` and `SessionEnd`, read the session transcript (`transcript_path`) and each helper
transcript (`<transcript dir>/<sid>/subagents/agent-<id>.jsonl`) from the stored byte offset to EOF.
**Claude Code writes one line per content block, each repeating the message's `usage`** (measured:
3,577 usage lines for 968 messages), so: dedupe by `(message.id, requestId)`, per message take the
max of each field (`input_tokens`, `output_tokens`, `cache_read_input_tokens`,
`cache_creation_input_tokens`); keep in `offsets-<sid>.json`, per transcript, the last 200 message ids
with the amounts already emitted and emit only deltas (a message's lines can straddle a Stop). Skip
`isSidechain: true` lines in the main transcript. Helper scope = the `agent-<id>` in the file name;
helper type from the sibling `.meta.json` if present, else the pairing map. Write one `cost` event
per (scope, model) with a non-zero delta, then store the new offsets. When the pass sees a
`custom-title` entry newer than the last one recorded, the `cost` event carries `title` (that is the
ledger's durable source of the session's sidebar title). `weighted` = `(in + out) × weight(model, in)` with the
weights of `dashboard/usage.py:model_weight` (copied into the hook config, `hooks/atlas_config.json`,
so the hook never imports the repo). A transcript that shrank resets its offset to 0. Lines that do
not parse are skipped. Cost reading must not block the Stop beyond 2 s: stop reading and keep the
offset where it got to.

### 1.6 v1 import (`tools/import_v1_ledger.py`)

Reads `<repo>\ledger\events.jsonl` (READ-ONLY; path overridable by `--src`), writes
`ledger/v1/events.jsonl` (overwritten on each run, idempotent): each original line becomes
`{"v": 1, "src": "v1", ...}` keeping **only an allowlist** of fields: `t, ev, job, project, lane,
phase, to, was, status, verdict, plan_task, branch, commit, tokens, cache_read, cache_write,
cache_creation, fresh, input, output, model, effort, duration_s, attempt, rework, findings, result,
kind, which, action, pass, estimate, type` (everything else, notably `task, notes, q, note, why,
error, diffstat, question, answer`, is dropped). Verdicts map `commit-ready → READY`,
`needs-changes → NEEDS_CHANGES`, `escalate → ESCALATE`. A v1 task's title = `plan_task`, else the job
id. Reports counts per kept/dropped field.

### 1.7 Task records (derived on read: `cockpit/ledger2/derive.py`)

A task runs from its opening event to the first of: its `task_done` (status `done`), the next opening
event in the same session (`switched`), `session_end` (`ended`), or nothing yet (`open`). v1 jobs
become tasks with `src: "v1"`, `type: "coding"`, area from the project (`areas.yaml` `projects`),
crew from their phases, verdicts from `review` events, status `done` when merged.

`duration_s` is the task's **active time**, not its wall-clock span: the union of (a) every helper interval
(`helper_start` or `helper_resume` to the matching `helper_end`, paired by `tuid`/`agent_id`; a helper with no end runs to
the task end) and (b) every gap between two consecutive events of the task (task open and task end included) of at most
`IDLE_GAP_S` = 15 minutes (`derive.py`). Longer gaps outside a helper interval count zero. `span_s` is the old wall-clock
value (`started` to `ended`, or to the last event while open). v1 imported tasks (`src: "v1"`) have no event detail:
`duration_s` = `span_s`. Carry-over notices (a `refusal` with `guard: "rework"` and a detail starting `carry-over`) carry
`notice: true` in the task's `refusals`.

```json
{
  "id": "abcd1234-2", "src": "v2", "sid": "...", "session_title": "Atlas v2 build",
  "area": "atlas", "type": "coding", "playbook": null, "plan_ref": "evt_0a1b2c3d", "plan_auto": false, "auto": false,
  "started": "...", "ended": "...", "duration_s": 5400, "span_s": 7200, "status": "done",
  "crew": ["implementer", "test-runner", "reviewer"],
  "helpers": [{"helper": "implementer", "count": 2, "labels": ["Build ledger store"]}],
  "rounds": {"needs_changes": 1, "budget": 2, "granted": 0, "left": 1, "own": 1, "carried": 0},
  "verdicts": [{"t": "...", "helper": "reviewer", "verdict": "NEEDS_CHANGES", "version": 4, "findings": 3}],
  "final_verdict": "READY", "checked": true, "unverified_flag": false,
  "caught": 3, "edits": 9, "refusals": [{"guard": "rework", "would": true}],
  "cost": {"weighted": 1234567, "by_model": {"claude-opus-5-5": {"in": 0, "out": 0, "cache_read": 0, "cache_write": 0, "weighted": 0}},
           "by_helper": {"chief": 800000, "implementer": 300000}},
  "summary": {"goal": "...", "produced": "...", "decisions": "...", "open": "...", "review_min": 20}
}
```

* `rounds.own` = this task's own NEEDS CHANGES rounds, `rounds.carried` = rounds carried over from the previous unresolved
  task in the session (`needs_changes` = carried + own; `left` = budget + granted - needs_changes).
* `title` = the task's name: summary `goal`, else the first helper's first label (the description the main session gave it),
  else the session title, else null. The tasks endpoints (§5.2) replace it with `plan_title` when that resolves, so the field
  is the one name to show; `session_title` stays for a muted second line. A v1 job that never finished is `ended`
  (v1 is retired), with `ended` = its last event.
* `plan_ref` = the opening event's `plan_ref` (null when none); `plan_auto` = the opening event's `plan_auto` (true when the link was inferred, false otherwise). The tasks endpoints (§5.2) add `plan_title` to EVERY task: the
  Plan item's current title when the ref resolves (read-only, via `cockpit/plan/refs.py`, finished project-plan tasks included), else null.
  The Ledger tasks table shows a linked task as a muted "Plan:" prefix plus that title (its own name as the hover hint), so cost per Plan item is visible.
* A task is **resolved** when its latest verdict is a READY covering the latest main-session version (see the task-opening
  rules); an over-budget task without that carries into every chained re-declaration (a carried task has no verdict yet, so
  it cannot be re-declared into a fresh budget). A task that got NEEDS CHANGES and then a READY is resolved even when the
  main session never edited (`version` 0); main-session edits after the READY make it unresolved again, and so does a
  READY from a reviewer launched before the latest NEEDS CHANGES arrived.
* `checked` = the final version has a READY verdict (or an `ok` check, §1.2) at that version.
* `unverified_flag` = type with `needs_check: true` (incl. `undeclared`), status `done`, `switched`
  or `ended`, edits > 0 and not `checked` (the Ledger's safety net).
* Verdicts and helper ends are deduplicated by `agent_id`.
* `caught` = sum of `findings` over NEEDS_CHANGES verdicts.
* `auto` = the session has an `auto` event (its first command `: team-auto <marker>`, §7) whose
  marker exists in `ledger/auto/`.
* Cost of a task = `cost` events of the session between its start and end, by `scope`; helper cost
  attributes the helper's `agent_id` to its `helper` type.

## 5. The HTTP API (v2)

The v2 server is the existing `cockpit/server.py` with a seam (Wave 0): requests under `/api/v2/` go
to `cockpit/api_v2.py`, which routes by prefix to one lane module; static requests go to
`cockpit/web2_static.py` (served from `cockpit/web2/`) when the path is not `/api/…` and not under
`/v1/` (the old front end was removed on 2026-10-10 with the v1 wrap-up). Each lane module exposes:

```python
def get(path: str, query: dict[str, str]) -> tuple[int, dict] | None: ...   # None = not mine
def post(path: str, body: dict) -> tuple[int, dict] | None: ...
```

Routing is by prefix: `/api/v2/ledger/` → `ledger2.api`, `/api/v2/plan` → `plan.api`, everything
else → `shell_api`; each call is wrapped so one lane's exception is a 500 for that path only. A POST
body that is not valid JSON or not an object → `400 {"ok": false, "error": "body must be a JSON
object"}` before any lane sees it.
**Branch-server safety:** when `ATLAS_BRANCH_SERVER=1` (the branch server sets it with `ATLAS_NO_INBOX_SYNC=1`), server.py answers
`403 {"ok": false, "error": "read-only on the branch server"}` to every v1 write: POST
`/api/schedule/*`, `/api/plan/*` (v1), `/api/planner*`,
`/api/job/*`, `/api/dispatch*`, `/api/procedure`, `/api/monitor/*`, `/api/brain/*`.
`web2_static.serve(route, if_none_match)`: `/` → `index.html`; the path is resolved and must be
inside `cockpit/web2` (else 404); once `cockpit/web2/index.html` exists, a missing file is
`(404, …)`, never `None` (no silent fallback to a v1 file of the same name).
Errors: 400 bad input, 404 unknown id, 409 version conflict (§5.3), 500 unexpected (logged).
Every handler is fast (< 200 ms on today's data); anything slow is computed in a background thread
and served from a cache (ledger stats).

**Done sessions (2026-10-12, amended 2026-10-13).** The orchestrator closes a finished task with the no-op shell command `: team-done` (never from a helper). `hooks/team_events.py` matches it like the Atlas hook does: on the FIRST line of the command (capped at 200 characters), `^\s*:\s*team-done\b`, anything may follow (`: team-done now` and a `: team-done` followed by more lines count; `: team-doner` does not). It logs `{ev: "TeamDone", ts, sid, cwd}` and nothing else at PreToolUse, in the team-live log next to `WorkType`. In `teamlive`, a session is `done` when a main-session `TeamDone` (not `in_agent`) comes after its current task's opener (the latest `WorkType` or playbook command, the same anchor as the current-task window) AND no main-session (not `in_agent`) `UserPromptSubmit` comes after the last such `TeamDone`: when the operator writes again, the session stops being `done` (it is then working or waiting as usual) until the next `: team-done`. A newer opener also re-opens it, and a session with no opener is never `done`. `GET /api/v2/team` sessions carry `done` (bool). `waiting` is true only while the session is idle, the last main-session event is a Stop within 2 h AND the session is not `done`; `/api/v2/attention` follows `waiting`, so a done session reads `idle` there. `done` changes nothing else (`status`, hiding, timelines). The Team row shows a quiet `done` label where `waiting` would show. Known accepted limit: `TeamDone` is logged at PreToolUse, so in enforce mode a team-done refused by the done-lock still shows done until the next declaration or prompt; the ledger stays the record.

**Live helpers (2026-10-10).** A session is `working` when its main conversation is working OR at least one of its
helpers is live, background (`run_in_background`) or foreground alike. A helper is live when the event log has its
`SubagentStart` and no matching stop AND its own transcript (`<project folder>/<session id>/subagents/agent-<id>.jsonl`,
next to the session transcript) was written within `HELPER_FRESH` = 8 minutes of now. Measured helper transcripts
(44k consecutive records) show a median gap of 0.6 s and a 99th percentile of 57 s, but the full test suite runs about
5 minutes inside a single Bash call with no transcript write meanwhile, so the window is 8 minutes: a working
test-runner is not shown as gone, and a lost `SubagentStop` leaves a ghost for at most 8 minutes. A stale transcript closes the helper
at its last write. The transcript is the evidence because the hook log is silent while a helper edits and reads (only
Agent, Skill and `: team-*` calls are logged), so the older "no event for 10 minutes means gone" rule wrongly closed busy
background helpers and the session read "waiting" while they worked. When no transcript can be found the event-log rules
apply unchanged. When the session is working only because of helpers (`via_helpers`), the Team row reads
"working · N helper(s) in the background" (or "running" when any is foreground) with each live helper's creature
name and task label, the helper pipeline shows it as working, and `/api/v2/attention` counts the session as working,
not waiting. When the last helper finishes and the conversation is idle, the session returns to waiting or idle.

status `waiting` = idle with the last main-session event a Stop, within 2 h). The window split `usage.window_by_model()` once planned here was removed 2026-10-11 with the rest of the usage-window code. Nothing

### 6.2 Verdict capture
Helpers in this environment end with the `SubagentHandback` tool, so the final text may not be in
`last_assistant_message`. Sources, first that yields a match wins, **one verdict per `agent_id`**
(the hook records captured ids in state and ignores a second capture; `derive` dedupes too):
1. PreToolUse `SubagentHandback` fired inside a reviewer (`agent_type` in `reviewers`): the first
   line of `tool_input.message`;
2. SubagentStop of a reviewer: the first non-empty line of `last_assistant_message`;
3. a foreground PostToolUse Agent of a reviewer: the first line of `tool_response.content[].text`.
Match, case-insensitive: `^\W*(?:verdict\W*)?(READY|NEEDS[ _-]CHANGES|ESCALATE(?: TO OPERATOR)?)\b`
(`ESCALATE TO OPERATOR` = ESCALATE). No match → no verdict (a `helper_end` only). `findings` = count of
lines after the first that start with `-`, `*` or `<digit>.`

**Pairing a reviewer to its version:** PreToolUse Agent stores a pending entry `{tuid, helper,
version}`. SubagentStart (carries `agent_id`, `agent_type`) pairs with the **oldest unclaimed pending
entry of the same helper type** (the rule `teamlive` already uses, commit cc25e80) and logs
`helper_paired`. If the pairing is ambiguous, use the lowest pending version of that type: that can
cause a false send-back, never a false pass. An `agent_id` already paired never claims a pending entry (a resumed
helper logs `helper_paired` with `tuid: null` and keeps its record). "A real reviewer verdict was captured" is an explicit
pass condition of the record day (§6.7).

**How the command is read.** A linear, quote-aware pass (no backtracking regex on the command text; the pass stops at
200,000 characters and a longer command is refused as `oversized command`, fail closed): the text is split into
segments on unquoted `;` `&` `|` `(` `)` backticks and newlines, quotes removed, `#` comments and backslash-newline
continuations honoured (a backslash before `\n` or `\r\n` skips the whole line break), a backslash before a space kept inside the token (`/my\ dir/git`). The scan collects EVERY
publish in the whole command (not the first). Per segment:
* environment assignments and prefixes are skipped with the options that take a value, so the value is not read as the
  command: `sudo -u/-g ...`, `doas`, `env -u/-C ...` (`env -S "<string>"` is re-read as a command string), `nice -n`,
  `ionice`, `timeout [-s sig] [-k dur] DURATION`, `stdbuf`, `time`, `exec -a`, `nohup`, `command`, `setsid`, and the shell
  keywords `then do else if while ...`;
* the program name loses its path and `.exe`/`.cmd`/`.bat`/`.ps1` (`/usr/bin/git`, `git.exe`); a token holding a backslash
  outside quotes is also read with the backslashes removed (`g\it`), and backticks are also removed for a second whole-text
  pass (PowerShell's escape: `` gi`t ``); the hits of the two readings are merged by family (see the second reading below);
* wrappers are opened and the inner text read the same way, up to 4 levels deep (deeper = refused as `nested wrappers`):
  `bash|sh|zsh|dash|ksh -c` (also `-lc`, `-c -- '...'`), `cmd /c`, `powershell|pwsh` with `-Command`, `-EncodedCommand`
  (decoded), a `{ block }` or a bare string, `iex`/`Invoke-Expression`, `Invoke-Command`/`icm`,
  `Start-Process`/`saps`/`start` (FilePath plus ArgumentList split on commas), `eval`, `wsl [-e]`, `xargs` (options with
  a value skipped), `python -m <tool>`; package runners `npx|pnpx|bunx|uvx`, `npm|pnpm|yarn|bun dlx|exec|x`, `uv run`,
  `uv tool run`, `pipx run`, `poetry run` (their options with a value skipped, `@version` dropped from the package with an
  `@scope/` kept, `netlify-cli` read as `netlify`, `firebase-tools` as `firebase`, `npx -c "<shell command>"` re-read);
  `pnpm|yarn|bun <word>` that is not a package-manager subcommand is re-read as the command it runs
  (`pnpm wrangler deploy`);
* a double-quoted string that holds `$(...)` or a backtick, a here-string (`bash <<< "git push"`), and a heredoc body that
  a shell in the same command reads (`cat <<EOF | bash`) are scanned too. A heredoc body nobody executes (a commit
  message, `cat <<EOF > file`) is data and passes, except that (round 6) the body of an UNQUOTED delimiter that holds `$(` or a
  backtick is scanned too, because the shell expands it (`cat <<EOF` / `$(git push origin main)` / `EOF`). A `<<` after an unclosed `((`, `$((` or `$[` on its line
  (`echo $((1<<2))`) is an arithmetic shift, not a heredoc; a delimiter written `\EOF` is quoted like `'EOF'` and ends at `EOF`. Blocks, decided in the same pass where quoting is known: an UNQUOTED `{`
  that starts a token and an UNQUOTED `}` that ends a token (followed by a space, a line break, the end or one of `;&|()`)
  are segment boundaries like `;` and are dropped, so the contents of PowerShell and shell blocks are read as commands
  (`try { git push } catch { }`, `% { git push }`, `Measure-Command { ... }`, `function p { git push }`, `. { ... }`).
  A brace inside a token (`HEAD@{1}`, `${x}`, `@{u}`, `file.{a,b}`, `@{`) and every quoted brace (`-c "k={v}"`, `'{x}'`)
  stay plain text, and a closing `}` that balances a `{` of its own token is not a boundary. An unquoted `{#` stays text
  (so the `#` is not read as a comment), and an unquoted `{}` at a word start (`find . -exec rm {} ';'`, `{}/..`,
  `{}.d`) is kept as text, whatever follows it.
  **Second reading.** Whenever the text holds a brace it is read a second time in the PowerShell-braces mode, where EVERY
  unquoted `{` and `}` is a segment boundary, except the `${name}` variable syntax; quoting stays known, so a quoted brace is
  never a boundary in either reading. This catches blocks written without spaces (`%{git push}`, `try{git push}catch{}`,
  `.{git push}`, `if($x){a}else{git push}`, `do{git push}while($false)`, `$sb={git push}`, `-ScriptBlock{git push}`,
  `icm{git push}`, `function p{git push}`, `&{git push}x`). The reading is chosen ONCE per whole command, at the top: each
  reading (plain, PowerShell-braces; and each again without backticks) scans the whole tree of wrappers with that one
  reading, never forking at a nested level (a fork per level would cost 2 to the power of the depth and outlast the
  hook's timeout). The hits of the readings are merged by family: each family counts as often as the reading that saw it
  most, so every distinct publish takes an allowance. **Work budget:** the characters scanned over every wrapper level
  and every reading are summed; past 4 x 200,000 the scan stops and the command is refused as `unreadable command`
  (fail closed), so a command built to be slow is denied instead of timing out (a timed-out hook lets the command run).
  Harmless false positives of the second reading, kept: an unquoted brace before a dry-run flag
  (`git push {a,b} --dry-run`, `git push origin HEAD@{1} --dry-run`) is read as a plain `git push`.
  In the second reading a `#` right after a brace is never a comment (so `echo {#}; ...` cannot hide what follows);
  kept false positive: `&{x}#c; git push` is read with `#c` as text. Further odd-form limits are accepted: the gate
  targets ordinary and accidental publishes, not a determined adversary.
  **`find`.** `find ... -exec|-execdir|-ok|-okdir <command> ... ;|+` reads the tokens after each such flag, up to the
  terminator, as a command, like `xargs`. The terminators are the token `;` (quoted `';'`), `+`, and the lone `\` that is
  left of an unquoted `\;` (the unquoted `;` itself cuts the segment, as in the shell it would run; it is NOT turned into text,
  because in PowerShell `echo \; git push` really runs `git push`). The rest of a find after such a cut is a segment whose
  first word starts with `-`, `!` or `,` and that holds an exec flag; it is read as a find, so several `-exec` in one find
  are all read, also behind other primaries (`find . -exec true \; -print -exec git push \;`, `... ! -name x -exec ...`,
  `... , -exec ...`, `... -o -exec ...` are publishes; `find . -exec echo {} \; -exec echo git push \;` is not). Limits:
  a find run from a script or alias is not read; `-exec sh -c '...'` is read through `sh -c`; and any segment that starts
  with `-`, `!` or `,` and holds an exec flag is read as a find (`-print -exec git push \` after a `;`: false positive, kept).
  A PowerShell assignment prefix
  (`$x = ...`, `$null = ...`, `$x=...`) is skipped. **Known false positive (kept):** a double-quoted string that holds
  `$(...)` or a backtick is read as a command, so `echo "$(date) git push"` is treated as a publish.

A matcher that raises, or any failure to read the command, denies (`unreadable command`). **Exempt:** a segment that
starts with the documented `tools/anchor_ledger.py` (the bypass guard's own path rules: the Atlas checkout or one of its
worktrees, relative path only from such a cwd, no redirection or substitution): its push belongs to the approved anchor
design. A second command in another segment is judged on its own.
**Honest limits (the gate stops honest mistakes and the plain forms, not a determined bypass):** git aliases; scripts that
publish internally (`make deploy`, `npm run release`, `./deploy.sh`); `python -c` and other interpreters; `echo "git push"
| sh`; commands built at run time; **non-shell tools** (MCP servers, browser automation, an editor's own git); other
upload tools (`rsync`, `scp`, `curl -T`, `surge`, `railway` ...); and a **forged grant**: a script that writes the state
cache (`state/<sid>.json`) or the ledger directly is stopped only by rule B, the hash chain and the outside anchor, not by
this gate.

**The grant.** `/allow-publish` grants ONE publish, `/allow-publish N` grants N (1 to 5; more is clamped to 5). One
allowance = one publish: a command holding three publishes (`git push && gh pr merge 3 && npm publish`) needs three
allowances and is denied outright, without using any up, when fewer are left; when allowed, all are used up together and
each logs its own `publish_allowed {what}`. It is a user-only skill, a mirror of `/grant-rework` (§6.4):
`hooks/skills/allow-publish/SKILL.md` with `disable-model-invocation: true`, installed by `tools/install_hooks.py`; the
model invoking it through the Skill tool is denied in every mode (logged `ignored`); it is refused inside `CronCreate`,
`ScheduleWakeup` and `SendMessage` like the other two (`USER_ONLY_RE`); and it is honoured ONLY from UserPromptSubmit whose
prompt STARTS with `/allow-publish`, never from a helper, and only on an interactive entry (the `interactive_entries`
rule of §6.4a, same fixed fallback `cli`, `claude-desktop`, `claude-vscode`; otherwise `ignored` "publish grant from
non-interactive entry"). It needs no open task. The hook logs `publish_grant {n, expires, entry}`; state keeps `pub_n`
(allowances left, capped at 5 when grants add up) and `pub_exp`. A grant **expires 30 minutes after it was typed or when
the session ends** (`session_end` zeroes it), and it is per session. **Only the MAIN session can use it**: a helper's
publish command is always denied, with or without a grant, and does not use one up.

**The deny never waits for the ledger.** A hook that runs past its timeout lets the command through, so the DENY is decided
before the ledger lock is taken, from a lock-free read of the state cache (`pub_n`, `pub_exp`): no grant, a helper, a
missing or unreadable cache (a cold cache is never rebuilt here) all deny at once. Since 2026-10-13 the cache is also not
trusted to ALLOW: an open grant in the cache is confirmed by the ledger's own `publish_grant` / `publish_allowed` events
for this session (read from the end of today's and yesterday's day files, without the lock; see §6.4c), and a mismatch
denies and logs `ignored` ("grant not in ledger"). The lock is taken only to use up a
grant, with a short wait (about 0.5 s); a busy lock denies and leaves the grant untouched. The refusal is logged
afterwards, best effort (about 0.2 s of waiting for the lock, then an unlocked line flagged `nolock`; a missing cache is
not recreated; the refusal never saves state). Measured on the build machine, a denied `git push` takes about 0.4 s end to end (Python start-up included)
with the lock held and a cold cache, and about 1 s when a grant exists but the lock stays held.

**Tamper resistance (honest limit):** the ledger, the state cache and `atlas_config.json` are plain
files a model could still write through a shell command. Mitigations: Edit/Write/NotebookEdit to
`<data>\ledger\` and `~/.claude/hooks/atlas/` are denied in every mode; each hook run
compares the config's mode with the last `mode` event and logs `tamper` on a mismatch; the Ledger
shows the tamper count. So the locks stop honest mistakes and make tampering visible; they do not
make it impossible. (Raised to the operator with the screen review.)

### 6.4c The config gate and `/allow-config` (2026-10-13)
The operator's rule: the files that define how Claude sessions and agents behave change only with the operator's OK. **In EVERY mode**
(record and enforce alike, like the publish gate), an Edit, Write or NotebookEdit on a config path, and a Bash or
PowerShell command that changes one, is denied unless the operator holds an open grant in this session. Deny reason:
"Changing instructions, skills or settings needs the operator's OK: show the operator the exact change, then ask the operator to type
/allow-config." Precedence for an edit: the protected-path rule first (the ledger and hooks folders, "can't be edited"),
then this gate, then the exempt rule and the other guards. For a shell command: rule B (§6.4), then this gate, then the
publish gate (§6.4b), then the forged-grant check (§6.4a), then the `: team-*` handling. On a shell command this gate
only DENIES: an open grant lets the command past this gate and on to the checks after it, so a command that also publishes
needs a publish grant too, and `claude -p '/grant-rework'` is refused whatever grants are open. The allowance is logged
once per command.

**What is a config path** (`Hooks.is_config`, case-insensitive, on the path components):

  `~/.claude/profile.md`) or matches `settings*.json`.

Not config: `.claude/projects/**` (memory and transcripts stay free), `.claude/worktrees/**` (except the file-name rule),
everything else. The path forms of §6.5 apply: ANY form (absolute, real, stream-stripped) that matches counts. An edit on a

  `~\.claude\` (memory, plans, skills, settings), the session's scratchpad / the system
  temp dir, `<data>\`, and files whose name ends in `build-log.md` or `.notes.md`, and scratch files: a name that starts with `scratch-` and ends in `.md`, a name that ends in
  `.scratch.md`, or a `.md` / `.txt` file inside a folder named exactly `_scratch`. The path is normalised first;
  names match case-insensitively, on whole path components. Never scratch: any path with a component starting
  with `.` (`.claude`, `.github`), and the names `claude.md`, `claude.local.md`, `agent.md`, `agents.md`, `skill.md`,
  `gemini.md`, `cmakelists.txt`, `requirements.txt`. A config path (§6.4c) is never recorded as an `edit` either: it is
  gated instead.
* **Path forms (2026-10-13).** Every path check looks at TWO forms of the path: the absolute one (`norm_path`) and the
  real one (`realpath`, so junctions and symlinks are resolved; if it cannot be resolved the absolute form stands in),
  and the same two forms of each root (ledger dir, hooks dirs, anchor clone, exempt dirs). Fail-safe: a path is
  **protected** (ledger, hooks folders, anchor clone) when ANY form is under ANY form of a protected root, and is
  **config** (§6.4c) when ANY form matches; it is **exempt** only when EVERY form is exempt on its own (so a junction
  named `_scratch` that points at a source folder exempts nothing). NTFS alternate data streams: a path whose part after
  the drive holds a `:` (`x.md:s`, `file::$DATA`) is NEVER exempt or scratch; for the protected and config checks the
  stream suffix is stripped first (everything from the first `:` in the last component, and trailing dots and spaces), so
  `CLAUDE.md:x` is config and `ledger\file:x` is protected. `norm_path` itself is unchanged.
* **Closing:** PreToolUse `: team-done`: allowed when the task's type has `needs_check: false` and
  no edits, or `version == 0`, or a READY verdict (or ok check) exists at `version == current`.
  Otherwise refuse: `"Not closed: version <v> has no passing review (last READY at version <m>). Run
  the reviewer on the final version, then close."`
* **Stop send-back:** on Stop, if the current task is open, `needs_check` (or it has edits), `version
  > last_verified`, `stop_hook_active` is false, `sent_back_for != version`, **and no pending builder younger than 2 h
  is still running** (a builder `helper_start` with no `helper_end`): block once with
  `{"decision": "block", "reason": "Unchecked changes (version <v>, last check at <m>). Run the
  check now, or tell the operator plainly that the work is not checked yet."}` and set `sent_back_for =
  version`. Never more than once per version.

### 6.6 The quick-question lock
While the current task's type is `quick-question`: PreToolUse Edit/Write/NotebookEdit on a non-exempt
path → refuse `"A quick question can't change files: declare a type with a checker first (: team-type
coding|writing|chore …)."`; PreToolUse Agent with any type other than `scout` → refuse likewise.

### 6.7 Modes: record-only first
`atlas_config.json` → `"mode": "record"` or `"enforce"`. In **record** mode every guard computes its
decision, logs it (`refusal` / `sendback` with `would: true`) and **allows** (no deny, no block).
In **enforce** mode it denies/blocks and logs `would: false`. Exception in both modes: the model
invoking `grant-rework`, `ack-break`, `allow-publish` or `allow-config` is always denied, and so are a publish command without a grant (§6.4b) and a config change without a grant (§6.4c). Switch: `py -3.12 tools/hooks_mode.py record|enforce`
(edits the installed config, appends a `mode` event). Start = record. Enforce only after one full
day of records shows no wrong refusal **and** at least one real reviewer verdict captured with the
right version, and the interactive `CLAUDE_CODE_ENTRYPOINT` values recorded (the orchestrator checks, logs the
evidence in the build log).

### 6.8 Areas/look check
On PostToolUse Edit/Write of a file named `areas.yaml` or `look.css` inside a git repo that has
`tools/check_look.py`: run it (`<python.exe> <repo>/tools/check_look.py --json <file>`, 3 s timeout),
log a `check` event; if it fails, return `additionalContext` with the problems (both modes; it
informs, never blocks). An edit to `areas.yaml` or `workflows.yaml` also refreshes the hooks' JSON
fallback copies.

### 8.1 Shell contract
* **Routes:** `#/plan` (default), `#/team`, `#/ledger`. Shortcuts `p t l`
  (ignored while typing in a field). Nav order: Plan, Team, Ledger.
* **A screen module** default-exports `{id, title, key, mount(root, ctx), unmount()}`.
  `ctx = {api: {get(path), post(path, body)}, areas: [...], areaColor(id), every(ms, fn) /* poll,
  auto-cancelled on unmount */, kit, ui}`. A screen owns only its root element and its own CSS file
  (selectors prefixed with the screen id, e.g. `.ledger-…`).
* **Repaints** keep scroll position (save/restore `scrollTop` of the screen root and inner
  scrollers), and controls hold their values in module state so a poll can't clobber them.
* **Attention bar** (always visible, top): left `Atlas` + date; right chips `● <n> sessions working`
  (`--ok` dot), `● <n> waiting` (`--warn` dot, hidden at 0), `● <n> pending review` (`--accent`
  dot), polled every 10 s from `/api/v2/attention`.
* **Copy:** impersonal (no you/your/me, no personal names), no em-dashes in UI strings. Disabled controls show
  their reason in visible text next to them.
* **Cache-busting is automatic:** `web2_static.py` serves `index.html` with every local
  `href`/`src` given `?v=<first 10 hex of sha1(file bytes)>`, and injects an
  `<script type="importmap">` mapping every `.js` under `cockpit/web2/` to its `?v=` URL, so ES
  module imports are versioned too. Other files are served with `Cache-Control: no-cache` + ETag.
  No hand-bumped version numbers anywhere in v2.
